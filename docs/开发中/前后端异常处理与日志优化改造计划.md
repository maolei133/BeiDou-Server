# 异常处理与日志优化改造计划

## 1. 目标

1.  **统一异常响应格式**：后端所有接口的响应都采用标准的 JSON 结构。
2.  **区分业务异常与系统异常**：明确区分业务逻辑中的可预见“失败”（如Token过期）与系统运行时发生的意外错误。
3.  **优化日志级别**：将可预见的业务异常（如Token过期、权限不足、参数错误）的日志级别从 `ERROR` 降至 `WARN` 或 `INFO`，减少日志噪音，使 `ERROR` 级别的日志真正反映需要紧急修复的问题。
4.  **简化前端处理**：前端通过统一的响应拦截器处理所有API反馈，简化组件内的代码逻辑。

## 2. 现有问题分析

### 2.1 后端 `@gms-server`

*   **异常响应不统一**：部分代码直接抛出异常，部分返回特定HTTP状态码，前端处理逻辑分散。
*   **日志污染严重**：大量可预期的业务异常（如Token过期、非法参数、权限不足）被记录为 `ERROR` 级别，淹没了真正需要关注的系统级错误，增加了调试和运维的难度。如：
    *   `JwtUtils`: Token过期被记为 `ERROR`。
    *   `AuthEntryPointJwt`: 认证失败被记为 `ERROR`。
    *   `GlobalExceptionHandler`: `NoResourceFoundException` 等低优先级异常被记为 `ERROR`。

### 2.2 前端 `@gms-ui`

*   **错误处理分散**：尽管有拦截器，但页面组件中仍存在大量 `try-catch` 块用于显示错误信息，造成代码冗余。
*   **错误码不统一**：前端规范中成功码为 `20000`，但可能存在其他非标准用法。

## 3. 优化改造方案

### 3.1. 核心思想：分离“业务失败”与“系统错误”

*   **业务失败 (WARN/INFO)**：用户操作不当、权限不足、输入不合法等，是**程序正常运行的一部分**。后端应返回统一的JSON，并记录 `WARN` 或 `INFO` 级别的日志。
*   **系统错误 (ERROR)**：空指针、数据库连接失败、配置错误等，是**程序非预期的致命问题**。后端应返回统一的JSON，并记录 `ERROR` 级别的日志，附带完整堆栈。

### 3.2. 定义统一的 JSON 响应结构

```json
{
  "code": 20000,     // 业务状态码：20000 表示成功，非 20000 表示失败。
  "message": "操作成功", // 给用户的提示信息。
  "data": {},        // 成功时返回的数据体。
  "timestamp": 1678886400000, // 时间戳
  "path": "/api/user/login" // 请求路径
}
```
**`code` 字段约定：**
*   `20000`: 成功
*   `10001`: 参数校验失败
*   `20002`: Token 已失效或认证失败
*   `30001`: 权限不足
*   `40404`: 请求的资源不存在
*   `50000`: 系统内部错误

### 3.3. 后端 `@gms-server` 最终改造方案

#### 3.3.1. 统一异常入口：`GlobalExceptionHandler`

`GlobalExceptionHandler` 是统一日志级别和异常响应的关键，当前仓库最终实现使用 `ResultBody` 与 `BizException`：

*   **业务异常**：`BizException` 返回自身业务码；缺省码按参数错误归入 `10001`；日志为 `WARN`，不打印完整堆栈。
*   **参数校验**：`MethodArgumentNotValidException`、`BindException`、`HandlerMethodValidationException`、`MissingServletRequestParameterException`、`HttpMessageNotReadableException`、`IllegalArgumentException` 统一返回 `10001`；日志为 `WARN`。
*   **认证失败**：`AuthenticationException` 返回 `20002`；日志为 `WARN`。
*   **权限不足**：`AccessDeniedException` 返回 `30001`；日志为 `WARN`。
*   **资源不存在**：`NoResourceFoundException`、`NoHandlerFoundException` 返回 `40404`；日志为 `INFO`。
*   **请求方法/Servlet 异常**：按可预期请求失败返回 `10001`；日志为 `WARN`。
*   **未捕获系统异常**：通用 `Exception` 返回 `50000`；日志为 `ERROR`，保留完整堆栈。

#### 3.3.2. 改造安全组件

*   **`JwtUtils`**: Token 过期使用 `INFO`，签名无效、格式错误、不支持、空参数使用 `WARN`，不再记录 `ERROR`。
*   **`AuthEntryPointJwt`**: 未认证入口直接写出统一 JSON：`code=20002,message=认证失败或登录已失效,data=null,timestamp,path`，日志为 `WARN`。
*   **`JwtAccessDeniedHandler`**: 权限不足直接写出统一 JSON：`code=30001,message=权限不足，禁止访问,data=null,timestamp,path`，日志为 `WARN`。
*   **`AuthTokenFilter`**: 可预期认证失败清理安全上下文并继续交给 Spring Security 入口处理，不直接关闭响应流。

#### 3.3.3. 响应与业务异常类

*   **`ResultBody`**: 作为当前统一响应类，已包含 `code`、`message`、`data`、`timestamp`、`path`；兼容保留 `responseId`。
*   **`BizException`**: 作为当前业务异常类，对应早期计划中提到的 `BusinessException` 概念；业务失败不填充堆栈。
*   **成功码**: `BizExceptionEnum.SUCCESS` 固定为 `20000`。

### 3.4. 前端 `@gms-ui` 最终改造方案

#### 3.4.1. 强化 Axios 响应拦截器

`gms-ui/src/api/interceptor.ts` 是统一 API 反馈处理中心，当前规则如下：

*   `code === 20000`：视为成功，返回 `res.data`。
*   `code === 20002`：触发登录失效弹窗，并引导重新登录；HTTP `401` 同样走该逻辑。
*   `code === 30001`：统一权限不足警告；HTTP `403` 同样走该逻辑。
*   `code === 50000`：统一系统异常错误提示；HTTP `5xx` 同样按系统异常提示。
*   其他非 `20000` 业务失败：统一 `Message.warning` 提示，并向调用方抛出异常。
*   网络错误：提示无法连接服务器，请检查网络或服务状态。
*   文件下载：`responseType: 'blob'` 走下载分支，下载失败统一提示。

#### 3.4.2. 简化页面组件调用

移除页面组件中重复弹窗/消息提示的 `try-catch` 逻辑；调用方只保留加载态、空态、表单复位等局部 UI 收尾。

```typescript
// 改造后
const loadData = () => {
  setLoading(true);
  getAccountList(...)
    .then((data) => {
      // 处理成功数据
    })
    .catch(() => {
      // 此处为空，或只处理UI相关的失败状态，无需弹窗
    })
    .finally(() => {
      setLoading(false);
    });
};
```

## 4. 详细改造步骤计划

### 阶段一：后端基础框架改造

1.  **任务 1.1**: 更新 `GlobalExceptionHandler`，为 `BizException`, `MethodArgumentNotValidException`, `NoResourceFoundException`, `AccessDeniedException` 添加专门的处理方法，并**设置正确的日志级别（`WARN` 或 `INFO`）**。
2.  **任务 1.2**: 确保 `GlobalExceptionHandler` 中处理通用 `Exception` 的方法使用 `log.error` 并记录完整堆栈。
3.  **任务 1.3**: 审查并修改 `AuthEntryPointJwt`、`JwtAccessDeniedHandler` 和 `JwtUtils`，移除可预期认证/授权失败路径中的 `log.error`，改为统一 JSON 与 `WARN/INFO`。
4.  **任务 1.4**: 使用 `ResultBody` 和 `BizException` 承接统一响应与业务失败，统一成功码为 `20000`。

### 阶段二：前端基础框架改造

1.  **任务 2.1**: 强化 `src/api/interceptor.ts` 中的响应拦截器，使其能处理所有业务失败 `code`，并根据 `code` 执行不同操作（`Message` 提示或 `Modal` 弹窗）。
2.  **任务 2.2**: 定义 `ApiResponse` TypeScript 接口。

### 阶段三：模块化增量改造

1.  **任务 3.1 (用户认证模块)**:
    *   **后端**: 改造 `AuthController`/`AuthService` 登录失败逻辑，认证失败统一返回 `code=20002` 和规范响应结构。
    *   **前端**: 改造登录页面，移除重复错误提示，简化 API 调用。
2.  **任务 3.x**: 按模块（玩家、商城、背包等）依次进行前后端改造。

### 阶段四：收尾与验证

1.  **任务 4.1**: 进行回归测试，特别关注Token过期、权限不足、参数错误等场景。
2.  **任务 4.2**: **验证Loki日志系统**，确认业务失败（如Token过期）被记录为 `WARN`，而系统内部错误（如空指针）被记录为 `ERROR`。
3.  **任务 4.3**: 清理项目中遗留的错误处理代码，并更新开发规范文档。

## 6. 进度中心队列下发拆分

以下任务必须全部进入进度中心队列，按依赖顺序推进：

1. **P1 / 高 / 后端**：后端统一响应与异常基线梳理。确认现有 `ResultBody`、`BizException`、`GlobalExceptionHandler`、Spring Security 入口的实际代码位置与缺口。
2. **P1 / 高 / 后端**：改造 `GlobalExceptionHandler`，按业务失败/系统错误拆分日志级别和统一响应结构。
3. **P1 / 高 / 后端安全**：改造 `JwtUtils`、`AuthEntryPointJwt` 与权限异常路径，避免 Token/认证失败刷 `ERROR`。
4. **P1 / 中 / 前端**：强化 Axios 响应拦截器与 `ApiResponse` 类型，统一处理 `20000`、`20002`、`30001`、`10001`、网络错误。
5. **P2 / 中 / 跨端**：认证登录模块前后端联调，移除页面重复错误提示，验证账号密码错误、Token 过期、权限不足。
6. **P2 / 中 / 跨端**：按玩家、商城、背包、日志等模块增量迁移页面错误处理和后端业务异常。
7. **P1 / 中 / QA/Ops**：异常与日志级别回归，覆盖接口响应、前端提示、Loki 日志级别、敏感字段脱敏。
8. **P2 / 低 / 文档**：更新开发规范、接口规范和日志规范，回填本计划执行结果。
