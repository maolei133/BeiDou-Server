# 异常处理与日志优化改造计划

## 1. 目标

1.  **统一异常响应格式**：后端所有接口的响应都采用标准的 JSON 结构。
2.  **区分业务异常与系统异常**：明确区分业务逻辑中的可预见“失败”（如Token过期）与系统运行时发生的意外错误。
3.  **优化日志级别**：将可预见的业务异常（如Token过期、权限不足、参数错误）的日志级别从 `ERROR` 降至 `WARN` 或 `INFO`，减少日志噪音，使 `ERROR` 级别的日志真正反映需要紧急修复的问题。
4.  **简化前端处理**：前端通过统一的响应拦截器处理所有API反馈，简化组件内的代码逻辑。

## 2. 现有问题分析

### 2.1 后端 `@gms-server`

*   **异常响应不统一**：部分代码直接抛出异常，部分返回特定HTTP状态码，前端处理逻辑分散。
*   **日志污染严重**：大量可预期的业务异常（如Token过期、非法参数、权限不足）被记录为 `ERROR` 级别，淹没了真正需要关注的系统级错误，增加了调试和运维的难度。如：
    *   `JwtUtils`: Token过期被记为 `ERROR`。
    *   `AuthEntryPointJwt`: 认证失败被记为 `ERROR`。
    *   `GlobalExceptionHandler`: `NoResourceFoundException` 等低优先级异常被记为 `ERROR`。

### 2.2 前端 `@gms-ui`

*   **错误处理分散**：尽管有拦截器，但页面组件中仍存在大量 `try-catch` 块用于显示错误信息，造成代码冗余。
*   **错误码不统一**：前端规范中成功码为 `20000`，但可能存在其他非标准用法。

## 3. 优化改造方案

### 3.1. 核心思想：分离“业务失败”与“系统错误”

*   **业务失败 (WARN/INFO)**：用户操作不当、权限不足、输入不合法等，是**程序正常运行的一部分**。后端应返回统一的JSON，并记录 `WARN` 或 `INFO` 级别的日志。
*   **系统错误 (ERROR)**：空指针、数据库连接失败、配置错误等，是**程序非预期的致命问题**。后端应返回统一的JSON，并记录 `ERROR` 级别的日志，附带完整堆栈。

### 3.2. 定义统一的 JSON 响应结构

```json
{
  "code": 20000,     // 业务状态码：20000 表示成功，非 20000 表示失败。
  "message": "操作成功", // 给用户的提示信息。
  "data": {},        // 成功时返回的数据体。
  "timestamp": 1678886400000, // 时间戳
  "path": "/api/user/login" // 请求路径
}
```
**`code` 字段约定：**
*   `20000`: 成功
*   `10001`: 参数校验失败
*   `20002`: Token 已失效或认证失败
*   `30001`: 权限不足
*   `40404`: 请求的资源不存在
*   `50000`: 系统内部错误

### 3.3. 后端 `@gms-server` 改造计划

#### 3.3.1. 改造 `GlobalExceptionHandler` (核心)

这是统一日志级别的关键。

```java
// 示例代码 (Java)
@Slf4j
@ControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 处理自定义业务异常 (日志级别：WARN)
     */
    @ExceptionHandler(BusinessException.class)
    @ResponseBody
    @ResponseStatus(HttpStatus.OK)
    public Result<?> handleBusinessException(HttpServletRequest request, BusinessException e) {
        log.warn("业务异常 - Code: {}, Message: '{}', Path: {}", e.getCode(), e.getMessage(), request.getRequestURI());
        return Result.error(e.getCode(), e.getMessage(), request.getRequestURI());
    }

    /**
     * 处理参数校验异常 (日志级别：WARN)
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseBody
    @ResponseStatus(HttpStatus.OK)
    public Result<?> handleValidationException(HttpServletRequest request, MethodArgumentNotValidException e) {
        String errorMessage = e.getBindingResult().getAllErrors().get(0).getDefaultMessage();
        log.warn("参数校验失败 - Message: '{}', Path: {}", errorMessage, request.getRequestURI());
        return Result.error(10001, "参数校验失败: " + errorMessage, request.getRequestURI());
    }

    /**
     * 处理资源未找到异常 (日志级别：INFO)
     */
    @ExceptionHandler(NoResourceFoundException.class)
    @ResponseBody
    @ResponseStatus(HttpStatus.OK)
    public Result<?> handleNoResourceFoundException(HttpServletRequest request, NoResourceFoundException e) {
        log.info("请求资源未找到 - Path: {}, User-Agent: {}", request.getRequestURI(), request.getHeader("User-Agent"));
        return Result.error(40404, "请求的资源不存在", request.getRequestURI());
    }
    
    /**
     * 处理权限不足异常 (日志级别：WARN)
     */
    @ExceptionHandler(AccessDeniedException.class)
    @ResponseBody
    @ResponseStatus(HttpStatus.OK)
    public Result<?> handleAccessDeniedException(HttpServletRequest request, AccessDeniedException e) {
        log.warn("权限不足 - User: {}, Path: {}", SecurityContextHolder.getContext().getAuthentication().getName(), request.getRequestURI());
        return Result.error(30001, "权限不足，禁止访问", request.getRequestURI());
    }

    /**
     * 处理所有其他未捕获的系统异常 (日志级别：ERROR)
     */
    @ExceptionHandler(Exception.class)
    @ResponseBody
    @ResponseStatus(HttpStatus.OK)
    public Result<?> handleGlobalException(HttpServletRequest request, Exception e) {
        log.error("系统内部错误 - Path: {}", request.getRequestURI(), e); // 记录完整堆栈
        return Result.error(50000, "系统内部错误，请联系管理员", request.getRequestURI());
    }
}
```

#### 3.3.2. 改造安全组件

修改 `JwtUtils` 和 `AuthEntryPointJwt`，使其不再自行记录 `ERROR` 日志，而是抛出异常交由 `GlobalExceptionHandler` 处理。

*   **`JwtUtils`**: 在捕获到 `ExpiredJwtException` 等异常时，应直接向上抛出特定的 `AuthenticationException` 子类，而不是 `log.error`。
*   **`AuthEntryPointJwt`**: `commence` 方法是认证失败的入口。它应该将认证失败的响应构建委托给 `GlobalExceptionHandler`。一种实现方式是直接在 `commence` 方法中构建 `Result` 对象并返回，同时使用 `log.warn` 记录。

#### 3.3.3. 定义 `BusinessException`

保持不变，用于业务代码中主动抛出业务失败。

### 3.4. 前端 `@gms-ui` 改造计划

#### 3.4.1. 强化 Axios 响应拦截器

`src/api/interceptor.ts` 成为唯一的错误处理中心。

```typescript
// 示例代码 (TypeScript)
// ... (代码与上一版相同，核心是判断 res.code === 20000)
service.interceptors.response.use(
  (response) => {
    const res = response.data as ApiResponse;
    if (res.code === 20000) {
      return res.data; // 成功
    }
    
    // 根据 code 执行不同操作
    if (res.code === 20002) { // Token 失效
      // 弹窗提示，引导重新登录
    } else {
      // 其他业务失败，统一 Message 提示
      Message.error(res.message);
    }
    
    return Promise.reject(new Error(res.message));
  },
  (error) => {
    // 处理网络错误、HTTP 5xx 等
    Message.error('网络或服务器错误，请稍后重试');
    return Promise.reject(error);
  }
);
```

#### 3.4.2. 简化页面组件调用

移除所有页面组件中的 `try-catch` 错误提示逻辑。

```typescript
// 改造后
const loadData = () => {
  setLoading(true);
  getAccountList(...)
    .then((data) => {
      // 处理成功数据
    })
    .catch(() => {
      // 此处为空，或只处理UI相关的失败状态，无需弹窗
    })
    .finally(() => {
      setLoading(false);
    });
};
```

## 4. 详细改造步骤计划

### 阶段一：后端基础框架改造

1.  **任务 1.1**: 更新 `GlobalExceptionHandler`，为 `BusinessException`, `MethodArgumentNotValidException`, `NoResourceFoundException`, `AccessDeniedException` 添加专门的处理方法，并**设置正确的日志级别（`WARN` 或 `INFO`）**。
2.  **任务 1.2**: 确保 `GlobalExceptionHandler` 中处理通用 `Exception` 的方法使用 `log.error` 并记录完整堆栈。
3.  **任务 1.3**: 审查并修改 `AuthEntryPointJwt` 和 `JwtUtils`，移除其中的 `log.error`，改为抛出异常或直接使用 `log.warn`。
4.  **任务 1.4**: 定义 `Result` 和 `BusinessException` 类，统一成功码为 `20000`。

### 阶段二：前端基础框架改造

1.  **任务 2.1**: 强化 `src/api/interceptor.ts` 中的响应拦截器，使其能处理所有业务失败 `code`，并根据 `code` 执行不同操作（`Message` 提示或 `Modal` 弹窗）。
2.  **任务 2.2**: 定义 `ApiResponse` TypeScript 接口。

### 阶段三：模块化增量改造

1.  **任务 3.1 (用户认证模块)**:
    *   **后端**: 改造 `LoginController`，将认证失败逻辑改为抛出 `new BusinessException(20003, "账号或密码错误")`。
    *   **前端**: 改造登录页面，移除 `try-catch` 中的错误提示，简化API调用。
2.  **任务 3.x**: 按模块（玩家、商城、背包等）依次进行前后端改造。

### 阶段四：收尾与验证

1.  **任务 4.1**: 进行回归测试，特别关注Token过期、权限不足、参数错误等场景。
2.  **任务 4.2**: **验证Loki日志系统**，确认业务失败（如Token过期）被记录为 `WARN`，而系统内部错误（如空指针）被记录为 `ERROR`。
3.  **任务 4.3**: 清理项目中遗留的错误处理代码，并更新开发规范文档。
