# 全服物品统一持久化与溯源系统设计文档

> **开发规范**：所有代码的 Javadoc、注释以及开发过程中的回答、交流均必须使用**中文**。

## 1. 概述

### 1.1 背景
当前服务器的物品管理（背包、仓库、雇佣商店）存在数据存储耦合、依赖内存状态、缺乏统一流水等问题，这不仅带来了数据安全风险（如回档、复制），也使得物品流转追溯和玩家服务（如物品找回）难以实现。

### 1.2 核心目标
为解决上述问题，本项目将实施一套全新的物品持久化与溯源架构，旨在达成以下核心目标：
1.  **数据安全与一致性**：采用“中央账本”模式，所有物品操作实时落库，消除因服务器异常关闭导致的数据丢失风险。
2.  **架构解耦**：将仓库、雇佣商店等系统的物品存储从臃肿的 `inventoryitems` 表中彻底剥离，实现独立、可扩展的存储。
3.  **全生命周期可溯源**：建立统一的物品流转日志系统，记录任何物品从创建、交易、存储到消耗或销毁的全过程。
4.  **支持性业务创新**：基于新架构，实现**物品找回**、跨区共享仓库、Web端管理等高级功能。
5.  **标准化**：统一所有物品的唯一标识字段为 `uid`，为全系统数据打通奠定基础。

## 2. 核心架构设计

### 2.1 全局唯一标识 (UID)
*   **定义**：为游戏中每一个需要追踪的物品实例分配一个全服唯一的“身份证号”。
*   **字段名**：统一命名为 `uid`。
*   **数据类型**：`BIGINT`。
*   **生成策略**：采用 **Snowflake (雪花算法)** 生成，确保高性能和唯一性。
*   **懒加载机制 (Lazy Generation)**：
    1.  修改核心 `Item` 类，增加 `uid` 字段。
    2.  从数据库加载旧物品数据时，`uid` 字段为 `null`。
    3.  当物品首次进入**任何新架构的系统**（如存入新仓库、上架新商店）时，检查其 `uid`。若为 `null`，则立即生成一个新的 `uid` 并赋予该物品实例。此 `uid` 将伴随物品的整个生命周期。
    4.  **关键**：当物品从新系统流转回旧系统（如从仓库取回至背包）时，其 `uid` **必须**被持久化到 `inventoryitems` 表中新增的 `uid` 字段，否则溯源链将断裂。

### 2.2 存储模型：混合模式 (Hybrid Approach)
兼顾索引查询性能与数据完整性，所有新系统的物品存储均采用此模式。
*   **数据库字段**：存储 `uid`, `item_id`, `quantity` 等用于高效查询和索引的核心字段。
*   **JSON 快照**：将物品的完整属性（包括潜能、星级、制造者、有效期等）序列化为 JSON 字符串，存储在 `item_data` 字段中。
*   **原则（重要更新）**：为节省存储空间，`uid` 和 `item_id` **仅通过独立的数据库列进行持久化**，**禁止**将其写入 `item_data` JSON 内部。

### 2.3 日志策略：三层分离
1.  **业务流水 (MySQL)**：仅为需要**在游戏内向玩家展示**的记录创建数据库表，如 `hired_merchant_transactions`（用于显示销售记录）。
2.  **溯源日志 (MySQL + File)**：用于GM审计和物品追踪。
    *   **热数据**：`item_trace_logs` 表，存储近期（如30天）的详细流转记录。
    *   **冷数据**：全量日志以 JSON Lines 格式写入本地文件 (`logs/trace/`)，用于长期归档和大数据分析。
3.  **监控日志 (Loki)**：用于运维层面的实时监控和告警。记录高级别的操作摘要，如 `PLAYER_SELL_ITEM`, `STORAGE_TAKE_MESO`，但不包含完整的物品快照。

### 2.4 增量同步机制 (Diff & Sync) - **核心更新**
为了提高性能并确保数据一致性，物品持久化逻辑已从“全量删除后插入”升级为“增量同步”。

*   **核心类**：`org.gms.service.ItemFactoryService`
*   **方法**：`saveItems`
*   **逻辑流程**：
    1.  **快照查询**：首先根据 `type` (如背包、仓库) 和 `accountId/characterId` 查询数据库中现有的所有物品记录（获取 `inventoryitemid` 和 `uid`）。
    2.  **内存比对**：遍历当前内存中的物品列表：
        *   **匹配 (Update)**：如果内存物品的 `inventoryItemId` 或 `uid` 在数据库中存在，则执行 `UPDATE` 操作，更新数量、位置、属性等。
        *   **新增 (Insert)**：如果内存物品在数据库中不存在，则执行 `INSERT` 操作，并回填生成的 `inventoryItemId` 到内存对象。
        *   **跨类型移动 (Move)**：如果通过 `uid` 发现物品存在但属于不同的 `type`（例如从商城移动到背包），则执行 `UPDATE` 操作修改其 `type` 和归属权 (`accountId` vs `characterId`)，实现“抢夺”式更新。
    3.  **清理 (Delete)**：计算差集，将数据库中存在但内存中已消失的物品记录（且未被标记为跨类型移动）执行 `DELETE` 操作。
*   **优势**：
    *   **性能提升**：减少了大量的 `DELETE` 和 `INSERT` 操作，仅对变更数据进行 SQL 交互。
    *   **ID 稳定**：物品的 `inventoryitemid` 保持不变，有利于日志关联和外键约束。
    *   **防丢数据**：通过 `uid` 追踪跨类型移动，防止因并发或逻辑错误导致的物品丢失。

## 4. 关键系统模块设计

### 4.1 物品找回系统 (Item Recovery System)
*   **触发时机**：
    *   `Shop.sell()`: 当玩家向NPC商店出售物品时。
    *   `InventoryManipulator.drop()`: 当玩家丢弃物品时。
*   **核心逻辑**：
    1.  **价值判断**：在上述方法中，增加一个 `isValuableForRecovery(Item item)` 的判断逻辑。只有被认定为“有价值”的物品（如高等级装备、稀有消耗品，排除普通药水、杂物等）才会进入找回流程。
    2.  **记录日志**：如果物品有价值，则：
        *   获取物品的完整 `item_data` (JSON)。
        *   向 `item_recovery_logs` 表中插入一条新记录，`status` 为 `RECOVERABLE`，并设定 `recovery_deadline` (例如，当前时间 + 24小时)。
*   **找回流程**：
    1.  玩家与“失物招领处”NPC对话。
    2.  后端查询 `item_recovery_logs` 表中属于该玩家且 `status = 'RECOVERABLE'` 的所有记录。
    3.  将物品列表展示给玩家，玩家选择要找回的物品。
    4.  玩家支付少量手续费（金币）。
    5.  后端执行事务：
        *   将 `item_recovery_logs` 中对应记录的 `status` 更新为 `RECOVERED`。
        *   从 `item_data` 字段反序列化出 `Item` 对象。
        *   将物品发放回玩家背包。
*   **自动清理**：
    *   一个后台定时任务每日执行，将 `recovery_deadline < NOW()` 且 `status = 'RECOVERABLE'` 的记录更新为 `EXPIRED`。

### 4.2 仓库系统 (Storage System)
*   **数据迁移**：采用**懒加载迁移**。玩家首次与仓库NPC对话时，系统检测并执行一次性的数据迁移，从 `inventoryitems` 迁移至 `storage_items`，并为所有物品补全 `uid`。
*   **存入 (Store)**：
    1.  **安全检查**：
        *   检查物品是否为现金道具 (`isCash`)，若是则禁止存入。
        *   检查物品是否不可交易 (`isUntradeable`) 或固有道具 (`isDropRestricted`)，若是则禁止存入。
        *   检查物品是否为任务道具 (`isQuestItem`)，若是则禁止存入。
    2.  **堆叠处理**：
        *   **可充值道具 (飞镖/子弹)**：跳过堆叠逻辑，强制作为新条目存入，保留其独立属性。
        *   **普通可堆叠物品**：在仓库中查找相同 `itemId` 且未满堆叠的记录，优先合并。
            *   合并时更新数据库中现有记录的数量和 `item_data`。
            *   若有剩余或无匹配记录，则插入新记录。
    3.  **UID处理**：
        *   若物品被合并，其原始 `uid` 实际上被“销毁”，数据库保留目标堆叠的 `uid`。
        *   若插入新记录，检查 `uid` 是否已存在。若存在（冲突），则生成新 `uid` 后插入。
    4.  **事务操作**：
        *   开启事务：从背包表删除 -> (更新现有记录 OR 插入新记录到 `storage_items`)。
        *   提交事务。
    5.  **日志记录**：调用 `TraceabilityService.log()` 记录 `STORAGE_IN` 日志。
*   **取出 (Take)**：
    1.  **空间检查**：检查玩家背包是否有足够空间容纳取出的物品。
    2.  **事务操作**：
        *   开启事务：从 `storage_items` 读取并删除 -> 反序列化 `item_data` -> 插入背包表（**必须包含 `uid`**）。
        *   提交事务。
    3.  **日志记录**：调用 `TraceabilityService.log()` 记录 `STORAGE_OUT` 日志。
*   **整理 (Arrange)**：
    1.  **内存排序**：在内存中对物品进行合并和排序。
        *   **注意**：可充值道具（飞镖/子弹）在整理时**不合并**，保持独立条目。
    2.  **全量同步 (Diff Sync)**：
        *   获取数据库中该仓库的所有 `uid`。
        *   遍历内存列表：若 `uid` 存在则更新（数量、位置），若不存在则插入。
        *   删除数据库中存在但内存中已消失的 `uid` 记录。
        *   此过程在事务中完成，确保内存与数据库状态一致。

### 4.3 雇佣商店系统 (Hired Merchant System)
*   **双重日志**：
    1.  **保留** `hired_merchant_transactions` 表，用于游戏内“销售记录”查询。
    2.  **新增** 在上架、购买、取回等关键操作中，调用 `TraceabilityService.log()`，将物品流转信息写入统一的溯源系统。
*   **字段统一**：确保 `hired_merchant_items` 表中的唯一ID字段命名为 `uid`。

## 5. 前端与管理后台需求

### 5.1 仓库管理 (Web)
*   **功能**：允许管理员（或玩家在Web端）查看和管理仓库物品。
*   **接口**：
    *   `GET /api/storage/{charId}`: 获取指定角色的仓库物品列表。
    *   `POST /api/storage/move`: (管理员) 将物品从仓库移动到背包，或反之。

### 5.2 雇佣商店管理 (Web)
*   **功能**：查看全服活跃商店，搜索商店物品。
*   **接口**：
    *   `GET /api/merchant/list`: 获取活跃商店列表。
    *   `GET /api/merchant/{id}/items`: 获取商店内物品。
    *   `POST /api/merchant/close`: (管理员) 强制关闭违规商店。

### 5.3 溯源管理 (Web)
*   **功能**：全链路追踪物品流转。
*   **接口**：
    *   `GET /api/trace/history/{uid}`: 根据 UID 查询物品的所有流转历史（时间轴展示）。
    *   `GET /api/trace/search`: 根据物品ID、角色名、时间段搜索流转日志。
    *   `GET /api/trace/duplicates`: 查询疑似复制的物品（相同 UID 存在于多处）。

### 5.4 找回管理 (Web)
*   **功能**：查看玩家的可找回物品，人工干预找回。
*   **接口**：
    *   `GET /api/recovery/list`: 查询可找回记录。
    *   `POST /api/recovery/restore`: (管理员) 强制恢复物品给玩家（无视过期时间）。

## 6. 实施路线图

1.  **第一阶段：基础建设**
    *   **数据库**：编写并执行 `V2.0.0.1__create_traceability_system.sql`，创建新表并修改旧表。
    *   **核心类**：修改 `Item` 及其子类，增加 `uid` 字段。
    *   **服务层**：实现 `SnowflakeIdGenerator` 和 `TraceabilityService`。

2.  **第二阶段：仓库重构**
    *   重写 `Storage` 逻辑，实现 `storage_items` 的读写和懒加载迁移。
    *   对接 `TraceabilityService`。

3.  **第三阶段：物品找回系统开发**
    *   实现 `Shop.sell` 和 `InventoryManipulator.drop` 的拦截逻辑。
    *   开发找回 NPC 和后台清理任务。

4.  **第四阶段：现有系统对接**
    *   改造雇佣商店、玩家交易、怪物掉落等模块，全面接入 `uid` 和溯源日志。

5.  **第五阶段：后台支持**
    *   开发上述 Web 管理接口和前端页面。
