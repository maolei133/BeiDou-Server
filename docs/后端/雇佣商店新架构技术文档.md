# 雇佣商店 (Hired Merchant) 新架构技术文档

## 1. 架构概述

### 1.1 核心理念：中央账本 (Central Ledger)
新架构摒弃了旧系统依赖内存状态和分散存储（`inventoryitems` + `fredstorage`）的模式，采用了“中央账本”模型。
*   **数据驱动**：所有核心状态（开店、物品在售、已售、关闭）均以数据库记录为准，内存仅作为数据库的缓存和逻辑映射。
*   **事务保障**：关键操作（上架、购买、取回）均在数据库事务中完成，确保数据的一致性，彻底解决“物品丢失”和“复制”漏洞。
*   **全生命周期管理**：从创建到销毁，商店的每一个状态流转都有迹可循。

### 1.2 设计目标
1.  **零数据丢失**：通过实时持久化和事务机制，确保服务器崩溃或异常关闭时数据不丢失。
2.  **持久化在线**：支持服务器重启后自动恢复所有活跃商店，无需玩家重新开店。
3.  **可审计性**：记录每一笔交易流水，便于 GM 追踪和经济监控。
4.  **易维护性**：提供完善的后端管理接口和配置项，降低运维成本。

## 2. 数据库设计

新架构引入了三张核心表，完全独立于原有的 `inventoryitems` 表。

### 2.1 `hired_merchants` (商店主表)
记录商店的基本属性和生命周期状态。

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INT (PK) | 商店唯一标识 |
| `owner_id` | INT | 店主角色ID |
| `channel` | INT | 所在频道 |
| `map_id` | INT | 所在地图ID |
| `x`, `y` | INT | 坐标 |
| `description` | VARCHAR | 商店描述/店名 |
| `item_id` | INT | 雇佣商人道具ID (外观) |
| `status` | VARCHAR | **核心状态**：`ACTIVE` (活跃), `CLOSED` (已关闭), `EXPIRED` (已过期), `MAINTAINED` (维护中) |
| `start_time` | BIGINT | 开店时间戳 |
| `close_time` | BIGINT | 关闭时间戳 |
| `mesos` | BIGINT | 商店内累积的未取回金币 |

### 2.2 `hired_merchant_items` (物品表)
记录商店内的物品快照。

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INT (PK) | 物品记录ID |
| `merchant_id` | INT (FK) | 关联商店ID |
| `item_id` | INT | 物品模板ID |
| `quantity` | SMALLINT | 初始上架数量 (单组) |
| `bundles` | SMALLINT | 上架组数 |
| `sold_quantity` | SMALLINT | 已售出的组数 |
| `price` | INT | 单价 |
| `status` | VARCHAR | `ON_SALE` (在售), `SOLD_OUT` (售罄), `RETURNED` (已取回) |
| `item_data` | TEXT | **关键字段**：JSON格式存储物品的完整属性（潜能、强化等），实现与原背包表的解耦。 |

### 2.3 `hired_merchant_transactions` (交易流水表)
记录所有操作日志，用于审计和恢复。

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | INT (PK) | 流水ID |
| `merchant_id` | INT | 关联商店ID |
| `item_id` | INT | 关联物品记录ID |
| `buyer_id` | INT | 操作者ID (购买者或店主) |
| `type` | VARCHAR | `ADD` (上架), `BUY` (购买), `REMOVE` (下架), `RETURN` (取回) |
| `quantity` | SMALLINT | 操作数量 |
| `price` | INT | 交易单价 (仅 BUY 有效) |
| `total_price` | BIGINT | 总价 |
| `timestamp` | BIGINT | 操作时间 |

## 3. 核心业务流程

### 3.1 开店 (Open)
1.  **校验**：检查 `hired_merchants` 表中是否存在该玩家的 `ACTIVE` 记录。如果存在但内存中无对应实例，判定为“僵尸商店”，自动修正为 `CLOSED` 并提示玩家取回。
2.  **创建**：插入 `hired_merchants` 记录，状态为 `ACTIVE`。
3.  **实例化**：在内存中创建 `HiredMerchant` 对象并注册到 `World` 和 `Map`。
4.  **定时任务**：根据配置的持续时间，注册一个精确的定时关闭任务 (`scheduleClose`)。

### 3.2 上架 (Add Item)
1.  **扣除**：从玩家背包移除物品。
2.  **序列化**：将物品对象序列化为 JSON 字符串。
3.  **持久化**：在事务中插入 `hired_merchant_items` (ON_SALE) 和 `hired_merchant_transactions` (ADD)。

### 3.3 购买 (Buy)
1.  **校验**：检查库存是否充足。
2.  **事务执行**：
    *   更新 `hired_merchant_items` 的 `sold_quantity`。
    *   更新 `hired_merchants` 的 `mesos` (增加金币)。
    *   插入 `hired_merchant_transactions` (BUY)。
3.  **发放**：将物品发放给购买者。

### 3.4 关闭 (Close)
1.  **状态更新**：将 `hired_merchants` 状态更新为 `CLOSED`。
2.  **物品处理**：**不移动物品数据**。物品仍保留在 `hired_merchant_items` 表中，状态保持不变，等待取回。
3.  **特殊情况**：如果是服务器关闭 (`shutdown`)，且配置了重启恢复，则**不更新**数据库状态为 `CLOSED`，仅销毁内存对象。
4.  **通知与日志**：
    *   记录详细日志，包含店主名称、商店描述、关闭原因（玩家操作、过期、管理员强制、服务器关闭）。
    *   如果是非服务器关闭且玩家在线，发送弹窗或聊天栏通知。

### 3.5 取回 (Retrieve - Fredrick)
1.  **查询**：查找所有状态为 `CLOSED` 或 `EXPIRED` 的商店。
2.  **结算**：
    *   统计未取回金币 (`mesos`)。
    *   统计未售出且未取回的物品 (`bundles > sold_quantity` AND `status != RETURNED`)。
3.  **事务执行**：
    *   发放金币和物品给玩家。
    *   更新 `hired_merchants` 的 `mesos` 为 0。
    *   更新 `hired_merchant_items` 状态为 `RETURNED`。
    *   插入 `hired_merchant_transactions` (RETURN)。

### 3.6 重启恢复 (Restore on Restart)
1.  **启动加载**：服务器启动时，`World.loadActiveHiredMerchants()` 查询所有 `ACTIVE` 状态的商店。
2.  **重建**：根据数据库记录重建 `HiredMerchant` 对象，反序列化物品数据。
3.  **恢复**：将商店重新加入对应的频道和地图。
4.  **重调度**：调用 `rescheduleClose()`，根据当前配置重新计算剩余时间并注册定时关闭任务。

### 3.7 自动关闭与动态调控 (Auto-Close & Dynamic Rescheduling)
新架构采用了 **“精确定时任务 + 动态配置重调度”** 的方案，替代了传统的轮询检测。

1.  **精确定时**：每个商店在创建或恢复时，会根据 `hired_merchant_duration` 计算剩余时间，并注册一个一次性的 `ScheduledFuture` 任务。时间一到，立即触发关闭逻辑，误差控制在毫秒级。
2.  **动态调控**：
    *   `GameConfig` 监听 `hired_merchant_duration` 参数的变更。
    *   一旦参数修改，系统会触发 `Server.rescheduleHiredMerchants()`。
    *   该方法遍历所有活跃商店，取消旧的定时任务，根据新的持续时间重新计算剩余时间，并注册新的定时任务。
    *   如果重新计算后发现已过期，则立即关闭商店。
3.  **移除轮询**：原有的 `HiredMerchantTask` 轮询任务已被移除，因为新架构下数据实时持久化，且关闭逻辑已由精确定时任务接管。

## 5. 配置参数说明

所有参数均位于 `game_config` 表中，支持热加载。

| 参数名 | 类型 | 默认值 | 说明 |
| :--- | :--- | :--- | :--- |
| `hired_merchant_reload_on_restart` | Boolean | `true` | **核心开关**。是否在服务器重启后自动恢复活跃的雇佣商店。 |
| `hired_merchant_duration` | Integer | `1440` | 商店持续时长（分钟）。默认 24 小时。**支持热修改，修改后即时生效**。 |
| `hired_merchant_keep_days` | Integer | `30` | 历史数据（已关闭且已取回的商店及流水）保留天数，用于自动清理。 |
| `hired_merchant_max_items` | Integer | `16` | 单个商店允许上架的最大物品数量。 |
| `hired_merchant_tax_rate` | Integer | `0` | 交易税率（百分比）。 |
| `hired_merchant_allow_remote` | Boolean | `true` | 是否允许使用远程商店道具（如猫头鹰）打开商店。 |
| `hired_merchant_price_limit` | Long | `2147483647` | 单个物品的最高售价限制。 |
| `hired_merchant_meso_limit` | Long | `2147483647` | 商店累积金币上限，超过后无法继续售卖。 |

## 6. 后端管理接口 (API)

基础路径：`/api/merchant`

### 6.1 获取活跃商店列表
*   **URL**: `/list`
*   **Method**: `GET`
*   **描述**: 返回当前所有状态为 `ACTIVE` 的商店信息。
*   **返回**: `List<HiredMerchantsDO>`

### 6.2 获取商店物品详情
*   **URL**: `/{id}/items`
*   **Method**: `GET`
*   **参数**: `id` (Path Variable) - 商店ID
*   **描述**: 获取指定商店内的所有物品记录（包括已售出的）。
*   **返回**: `List<HiredMerchantItemsDO>`

### 6.3 恢复异常商店物品
*   **URL**: `/{id}/restore`
*   **Method**: `POST`
*   **参数**: `id` (Path Variable) - 商店ID
*   **描述**: 强制将指定商店内的未取回物品状态重置为 `ON_SALE`，并将商店状态置为 `CLOSED`。用于处理极少数情况下物品卡死的问题。
*   **返回**: String (成功/失败消息)

### 6.4 从本地备份恢复
*   **URL**: `/restore-backup`
*   **Method**: `POST`
*   **参数**: `filePath` (Query Param) - 本地 JSON 备份文件的绝对路径
*   **描述**: 当数据库严重故障时，可从 `logs/merchant_backup` 目录下的 JSON 文件恢复商店数据到数据库。
*   **返回**: String (成功/失败消息)

### 6.5 手动清理过期数据
*   **URL**: `/cleanup`
*   **Method**: `POST`
*   **参数**: `days` (Query Param, Default: 30) - 保留天数
*   **描述**: 手动触发数据清理任务，删除超过指定天数的已完结商店记录和交易流水。
*   **返回**: String (执行结果)

## 7. 运维与监控

### 7.1 日志审计
*   所有关键操作（开店、关店、恢复、过期）均记录在服务器日志中 (`log.info`)。
*   **日志增强**：日志中包含店主名称 (`ownerName`)、商店描述 (`description`)、商店ID (`merchantId`) 以及操作原因（如 `serverShutdown` 状态）。
*   所有交易明细均记录在数据库 `hired_merchant_transactions` 表中，支持 SQL 查询审计。

### 7.2 数据清理
*   系统内置 `HiredMerchantCleanupTask` 定时任务（每日运行一次）。
*   清理逻辑：删除 `close_time < (当前时间 - keep_days)` 且 `mesos = 0` 且所有物品均已 `RETURNED` 的商店记录及其关联数据。

### 7.3 容灾备份
*   **本地文件备份**：在 `HiredMerchant.forceClose` 发生异常时，系统会自动将商店数据序列化为 JSON 文件保存到 `logs/merchant_backup/` 目录，作为最后的恢复手段。

## 8. JSON 序列化注意事项

### 8.1 物品属性存储策略
为了减少数据库存储开销，`HiredMerchantService` 在序列化物品数据时采用了**按需存储**策略：
*   **稀疏存储**：仅保存非默认值的属性。例如，如果装备的 `str` 属性为 0，则不会写入 JSON。
*   **默认值回退**：反序列化时，如果 JSON 中缺少某个字段，对象将使用类定义的默认值（通常为 0 或 null）。
*   **安全性**：这种处理方式是安全的，且兼容未来新增属性（旧数据反序列化时新属性会自动使用默认值）。

### 8.2 特殊字段说明
*   **潜能 (Potential)**：目前代码中尚未发现潜能相关字段（如 `potential1`, `potential2`）。如果后续添加潜能系统，必须同步更新 `serializeItem` 和 `deserializeItem` 方法，否则潜能数据会在上架后丢失。

## 9. 未来扩展规划：物品流转追溯系统

### 9.1 现状与决策
当前架构**故意不序列化** `itemLog`（物品流转日志）到 JSON 中。
*   **原因**：`itemLog` 本质上是“将历史写入物品”的反模式，会导致 JSON 体积随流转次数无限膨胀，严重消耗数据库存储空间并降低 I/O 性能。
*   **结果**：物品从商店取回后，其旧的流转文本记录会丢失，但这为系统换取了极大的性能优势。

### 9.2 建议方案：唯一标识 + 外部日志
若后续需要建设全服物品追溯系统，应采用 **“身份证 + 档案局”** 的模式，而非“纹身”模式。

#### 1. 核心预留：全局唯一标识 (Global Unique ID)
*   **机制**：确保每个重要物品（装备、稀有道具）在生成时获得一个全局唯一的 ID（如 `uniqueId` 或扩展现有的 `sn` 字段）。
*   **持久化**：`HiredMerchantService` 的 JSON 序列化逻辑必须包含此 ID。
*   **现状**：当前代码已支持 `sn` 字段的序列化/反序列化，需确保普通装备也能分配到唯一的 `sn` 或新增 `uniqueId` 字段。

#### 2. 数据库扩展
*   **表结构优化**：在 `hired_merchant_items` 和 `hired_merchant_transactions` 表中新增 `item_unique_id` 索引列，用于快速定位特定物品的去向。
*   **独立日志表**：新建 `item_movement_logs` 表，记录 `log_id`, `item_unique_id`, `action` (上架/购买/取回), `from_char`, `to_char`, `timestamp`。

### 9.3 实施注意事项
1.  **严禁回退**：切勿为了追溯功能而重新将日志文本写入 JSON。
2.  **ID 连续性**：确保物品在“背包 -> 商店 -> 背包”的流转过程中，唯一 ID 保持不变（即反序列化时必须恢复原 ID，而不是生成新的）。
3.  **防复制监控**：利用唯一 ID，系统可定期扫描数据库，若发现同一个 `item_unique_id` 同时存在于两个不同的商店或玩家背包中，即可判定为复制 BUG 并自动封停。

## 10. 收入与税务说明

### 10.1 销售额与收入
*   **总销售额 (Total Sales)**：指商店售出物品的**税前**总金额。
*   **总收入 (Total Revenue)**：指扣除交易税后，店主实际获得的**税后**金额。
*   **金币提取规则**：玩家在商店营业期间通过“整理”功能取出的金币，**不会**导致总收入清零。总收入字段记录的是该商店生命周期内的累计净收益，仅在商店关闭并完全结算后归档。
