# 异常处理与日志级别规范

> 来源：`.gemini/rules/project_rules.md` 与 `docs/开发中/前后端异常处理与日志优化改造计划.md`。  
> 更新日期：2026-05-10  
> 适用范围：`gms-server` 管理 API、`gms-ui` Axios 调用链、与 API 相关的日志采集和回归验证。

## 1. 目标

- 后端管理 API 统一输出可被前端和运维复用的 JSON 响应结构。
- 明确区分业务失败与系统错误，避免 Token 过期、参数错误、权限不足等可预期场景污染 `ERROR` 日志。
- 前端通过统一 Axios 拦截器处理成功、业务失败、登录失效、权限不足、网络错误和文件下载。
- Loki/Promtail 与日志文件只把真正需要排查的系统异常提升为 `ERROR`。

## 2. 统一响应结构

标准 JSON 响应结构如下：

```json
{
  "code": 20000,
  "message": "操作成功",
  "data": {},
  "timestamp": 1678886400000,
  "path": "/api/user/login"
}
```

当前实现落点：

- 后端统一响应类：`gms-server/src/main/java/org/gms/model/dto/ResultBody.java`。
- 成功码来自 `BizExceptionEnum.SUCCESS`，固定为 `20000`。
- `ResultBody` 已填充 `code`、`message`、`data`、`timestamp`、`path`。
- 兼容字段：`responseId` 仍保留，用于请求链路追踪；文档和前端不得依赖它替代 `timestamp/path`。
- 文件下载接口可返回 `Blob`/文件流，不强制包 JSON；错误路径仍应尽量返回统一 JSON。

常用业务码：

| code | 含义 | 推荐日志级别 | 前端处理 |
| :--- | :--- | :--- | :--- |
| `20000` | 成功 | 不强制记录 | 拦截器返回完整响应体，页面用 `const { data } = await` 解构 |
| `10001` | 参数校验失败、请求体错误、请求方法不支持 | `WARN` | 统一警告提示 |
| `20002` | Token 失效、未认证、登录失败 | `WARN` 或 `INFO` | 统一登录失效弹窗或登录失败提示 |
| `30001` | 权限不足 | `WARN` | 统一权限不足警告 |
| `40404` | 请求资源不存在 | `INFO` | 统一提示或按静态资源缺失静默处理 |
| `50000` | 系统内部错误 | `ERROR`，记录完整堆栈 | 统一错误提示 |

## 3. 后端规则

1. `GlobalExceptionHandler` 是 MVC 异常响应和日志级别的统一入口。
2. 当前业务异常类为 `BizException`；历史计划文档中的 `BusinessException` 在本仓库中对应 `BizException`。
3. `BizException`、参数校验异常、认证异常、权限异常、资源不存在异常应作为业务失败处理，返回统一 JSON，不打印完整堆栈。
4. 通用 `Exception` 才按系统异常处理，返回 `50000`，日志使用 `ERROR` 并携带完整堆栈。
5. `AuthEntryPointJwt` 直接写出未认证统一 JSON，`code=20002`，日志使用 `WARN`。
6. `JwtAccessDeniedHandler` 直接写出权限不足统一 JSON，`code=30001`，日志使用 `WARN`。
7. `JwtUtils` 中 Token 过期记录 `INFO`，签名无效、格式错误、不支持、空参数记录 `WARN`，不得记录为 `ERROR`。
8. `AuthTokenFilter` 不应吞掉异常后关闭流；可预期认证失败应清理安全上下文并交给 Spring Security 入口返回统一 JSON。
9. 日志不得输出密码、Token、数据库连接串、完整玩家隐私信息、完整请求体等敏感字段。

## 4. 前端规则

1. `gms-ui/src/api/interceptor.ts` 是 API 成功/失败反馈处理中心。
2. `ApiResponse` / `ResultBody` 类型应覆盖 `code`、`message`、`data`、`timestamp`、`path`。
3. `code === 20000` 视为成功，拦截器返回完整响应体（`ApiResponse`），页面组件统一用 `const { data } = await api()` 或 `response.data` 解构获取内层 payload。
4. `code === 20002` 统一触发登录失效处理；HTTP `401` 也按登录失效处理。
5. `code === 30001` 或 HTTP `403` 统一提示权限不足。
6. `code === 50000` 或 HTTP `5xx` 统一提示系统异常。
7. 其他非 `20000` 业务失败统一使用 `Message.warning` 提示；页面组件只处理加载态、空态、局部失败状态，不重复弹错。
8. 文件下载请求通过 `responseType: 'blob'` 走下载分支，成功时保存文件，失败时统一提示下载失败。

## 5. 已回填实现状态

- `ResultBody` 已具备 `timestamp/path`，并保留 `responseId` 兼容旧调用。
- `GlobalExceptionHandler` 已按业务失败和系统错误拆分日志级别：业务失败 `WARN/INFO`，系统异常 `ERROR`。
- `AuthEntryPointJwt` 已返回 `code=20002` 的统一 JSON。
- `JwtAccessDeniedHandler` 已返回 `code=30001` 的统一 JSON。
- `JwtUtils` 已移除 Token 校验失败路径的 `ERROR` 日志。
- `gms-ui/src/api/interceptor.ts` 已按 `20000/20002/30001/10001/50000` 与 HTTP `401/403/5xx` 集中处理。
- `gms-ui/src/types/global.ts` 的 `ResultBody` 已包含 `timestamp/path`。
- `HiredMerchantController` 已改为返回 `ResultBody`，不再返回原始类型。
- 前端页面统一使用 `const { data } = await api()` 模式，已移除 `unwrapApiData` 等兼容函数。

## 6. 验收场景

- Token 过期或未认证：返回统一 JSON，`code=20002`，日志不出现 `ERROR`。
- 权限不足：返回统一 JSON，`code=30001`，日志为 `WARN`。
- 参数错误：返回统一 JSON，`code=10001`，前端统一提示。
- 静态资源或请求资源不存在：返回 `40404` 或合理静态处理，日志为 `INFO`。
- 未捕获系统异常：返回 `50000`，日志为 `ERROR` 且包含完整堆栈。
- Loki 查询能区分业务失败 `WARN/INFO` 与系统异常 `ERROR`。

## 7. 后续维护要求

- 新增 Controller 默认返回 `ResultBody.success(...)` 或抛出 `BizException`，避免直接返回字符串错误协议。
- 新增前端 API 默认走统一 Axios 实例，禁止页面绕过拦截器重复处理业务码。
- 修改响应码、日志级别或拦截器行为时，必须同步更新本规范和开发中计划文档。
- 当前仍需后续增量审查玩家、账号、商城、背包、百宝箱、掉落、溯源等模块的直接 `RuntimeException`、非统一响应和页面重复错误提示。
