# GMS 事件脚本开发指南

## 1. 概述

本文档旨在为开发者提供一个关于如何编写、维护和优化 GMS (Game Maple Story) 事件脚本的全面指南。事件脚本是实现各种游戏内活动、副本、Boss 战和自定义内容的核心。遵循本指南将有助于您编写出高效、稳定且易于维护的脚本。

## 2. 脚本环境与语法标准

我们的脚本引擎基于 **GraalVM JS**，完全支持 **ECMAScript 2024 (ES15)** 标准。这意味着您可以使用所有现代 JavaScript 的特性来编写更简洁、更强大的代码。

我们强烈推荐您使用现代语法，例如：

- **`const` 和 `let`**: 代替 `var` 来声明变量，以获得块级作用域和更清晰的意图。
- **箭头函数 (`=>`)**: 用于编写更简洁的函数表达式。
- **模板字符串 (`` ` ``)**: 使用反引号轻松拼接字符串和变量，例如 `` `你好, ${player.getName()}` ``。
- **解构赋值**: 快速从对象或数组中提取值。
- **类 (`class`)**: 使用面向对象的方式组织复杂逻辑。

**语法示例：**
```javascript
// 使用 const/let 定义常量和变量
const MAX_PLAYERS = 6;
let currentStage = 1;

// 使用模板字符串和箭头函数
const welcomeMessage = (player) => `欢迎, ${player.getName()}! 当前是第 ${currentStage} 阶段。`;

// 解构赋值
const [leader, ...members] = eim.getPlayers().toArray(); // 获取队长和其余成员
```

## 3. 核心概念与运行流程

### 3.1 核心对象

- **`em` (EventManager)**: 事件管理器。每个事件脚本（如 `Zakum.js`）都拥有一个独立的 `em` 实例。
- **`eim` (EventInstanceManager)**: 事件实例管理器。代表一个具体的、正在运行的事件副本。
- **`player` (Character)**: 玩家角色对象。

### 3.2 运行流程

1.  **服务器启动加载**: `EventScriptManager` 加载所有位于 `scripts/event` 目录下的 `.js` 文件。
2.  **注入与初始化**: 为每个脚本创建 `EventManager` 实例，并以 `em` 的名称注入，然后调用脚本的 `init()` 函数。
3.  **事件触发**: 玩家与 NPC 对话，NPC 脚本调用 `em.startInstance(...)`。
4.  **实例创建 (`setup`)**: `em` 调用事件脚本中的 `setup()` 函数，此函数**必须**返回一个 `EventInstanceManager` (`eim`) 对象。
5.  **事件开始**: Java 端获取 `eim`，注册参与者，并调用 `eim.startEvent()`，触发 `playerEntry` 等函数。
6.  **脚本逻辑执行**: 脚本通过 `eim` 控制事件流程。
7.  **事件结束 (`dispose`)**: 脚本**必须**调用 `eim.dispose()` 来结束事件并清理所有资源。

## 7. 性能与安全规范

### 7.1 <span style="color:red; font-weight:bold;">内存安全</span>

1.  **必须调用 `eim.dispose()`**: 任何事件，无论成功、失败或中途取消，都必须有逻辑路径能最终调用 `eim.dispose()`。这是释放地图、玩家、怪物等所有相关资源的关键。如果忘记调用，会导致这些对象常驻内存，引发严重的内存泄漏。
2.  **处理玩家离线**: 必须实现 `playerDisconnected` 和 `partyMemberRemoved` 函数，并在其中调用 `eim.unregisterPlayer(player)`。否则，断线的玩家对象将永远被 `eim` 引用，导致其占用的内存无法被回收。
3.  **正确取消定时任务**: 如果使用 `em.schedule` 创建了长期运行的全局任务，请务必在 `cancelSchedule` 函数中提供取消逻辑，以防脚本重载时产生重复的任务。对于 `eim.schedule` 创建的实例级任务，它们会在 `eim.dispose()` 时自动取消，无需手动处理。

### 7.2 <span style="color:orange; font-weight:bold;">CPU 性能</span>

1.  **谨慎使用高频函数**: `playerMovement` 函数会在玩家每次移动时被调用，频率极高。应避免在此函数中执行任何复杂或耗时的操作（如数据库查询、大量循环等）。
2.  **避免死循环和长循环**: 确保所有 `for` 和 `while` 循环都有明确的退出条件。在循环中避免进行网络或文件 I/O 等阻塞操作。
3.  **合理使用 `schedule`**: 对于需要等待的操作，应使用 `eim.schedule` 或 `em.schedule` 将其分解为多个异步步骤，而不是使用 `Thread.sleep()` 或忙等待（空循环）。`Thread.sleep()` 会阻塞整个脚本引擎线程，影响所有在该线程上运行的脚本。

    ```javascript
    // 错误示范：阻塞线程
    function badExample(eim) {
        eim.spawnMonster(...);
        java.lang.Thread.sleep(5000); // 阻塞了脚本线程5秒！严重影响性能！
        eim.spawnMonster(...);
    }

    // 正确示范：使用 schedule 异步执行
    function goodExample(eim) {
        eim.spawnMonster(...);
        eim.schedule("spawnNextWave", 5000); // 5秒后执行下一个函数，不阻塞当前线程
    }

    function spawnNextWave(eim) {
        eim.spawnMonster(...);
    }
    ```

### 7.3 <span style="color:blue; font-weight:bold;">线程安全</span>

- **共享引擎机制**: 系统底层采用的 GraalVM 共享引擎 (`SHARED_ENGINE`) 机制保证了不同脚本的 `Context` 是隔离的，但它们共享 JIT 等资源。
- **`SynchronizedInvocable`**: 系统已将脚本调用接口包装为线程安全的 `SynchronizedInvocable`，这意味着从 Java 端并发调用同一个脚本的不同函数是安全的。
- **脚本内部状态**: 尽管如此，您仍需注意脚本内部的全局变量。如果多个函数可能并发地修改同一个 JS 全局变量，您需要自行处理同步问题。**最佳实践**是使用 `eim.setProperty` 来管理状态，而不是依赖 JS 全局变量，因为 `eim` 内部对属性的读写是线程安全的。

### 7.4 <span style="color:red; font-weight:bold;">地图缓存释放</span> — 事件脚本性能关键

服务端使用 Caffeine 缓存管理地图实例（详见 `地图管理系统.md`）。无人地图在 60 秒后自动驱逐释放。这一机制对事件脚本有直接影响，开发时**必须遵守**以下规则，避免性能陷阱。

#### ① 禁止在脚本全局持有地图引用

```javascript
// ❌ 错误：init() 时 getMap 存入全局变量，全程持有引用
var myMap;
function init() { myMap = em.getChannelServer().getMapFactory().getMap(200090010); }
function takeoff() { myMap.warpEveryone(...); }  // myMap 可能已是游离对象

// ✅ 正确：每次使用时从缓存获取最新实例
const MAP_ID = { BOAT: 200090010 };
function getMap(id) { return em.getChannelServer().getMapFactory().getMap(id); }
function takeoff() { getMap(MAP_ID.BOAT).warpEveryone(...); }
```

**原因**：地图被驱逐后，全局变量指向的旧实例成为"游离对象"——玩家通过 `changeMap` 创建了新实例，但脚本仍操作旧实例，导致传送失效或 NPE。

#### ② 禁止在无人时加载地图

```javascript
// ❌ 错误：无条件 getMap 加载地图
function onCycle() {
    getMap(MAP_ID.WAITING_ROOM).warpEveryone(MAP_ID.TRANSPORT);
    getMap(MAP_ID.DOCK).setDocked(true);
}

// ✅ 正确：仅在缓存中已存在（有玩家）时才操作
function onCycle() {
    if (mapFactory().isMapLoaded(MAP_ID.WAITING_ROOM)) {
        getMap(MAP_ID.WAITING_ROOM).warpEveryone(MAP_ID.TRANSPORT);
    }
    if (mapFactory().isMapLoaded(MAP_ID.DOCK)) {
        getMap(MAP_ID.DOCK).setDocked(true);
    }
}
```

**原因**：周期性事件（如渡轮、电梯）每次循环调用 `getMap()` 会触发地图加载（WZ 解析、NPC 生成），60 秒后空置释放。即使加载开销不大（10-50ms/次），7 个事件 × 3 频道 × 多次/小时也会造成无效 CPU 消耗。

#### ③ 运输地图用 pinMap 保护航行期间

```javascript
const RIDE_MAPS = [MAP_ID.BOAT_DECK, MAP_ID.BOAT_CABIN];

function takeoff() {
    // 航行期间 pin，防止部分区域（如船舱）无人时被驱逐
    RIDE_MAPS.forEach(id => mapFactory().pinMap(id));
    // ... 玩家传送 + 倒计时 ...
}

function arrived() {
    // 抵达后解除 pin，允许正常驱逐
    RIDE_MAPS.forEach(id => mapFactory().unpinMap(id));
    // ... 玩家传送 + 清理 ...
}
```

**原因**：运输地图可能有多个分区（如船甲板 + 船舱）。玩家集中在甲板时，船舱无人 → 60 秒后释放 → 玩家走进船舱时地图已消失。航行期间 pin 住所有关联地图，抵达后立即解除。

#### ④ 倒计时用配置变量 + 避免反复加载

```javascript
// 顶部配置
const REBROADCAST_INTERVAL = 10000;   // 广播间隔（毫秒）
const COUNTDOWN_OFFSET_MS  = 3000;    // 提前量（毫秒），防客户端 00:00 时事件未触发

function broadcastCountdown() {
    const endTime = Number(em.getProperty("rideEndTime"));
    if (!endTime) return;
    const sec = Math.max(1, Math.floor((endTime - Date.now()) / 1000) - Math.ceil(COUNTDOWN_OFFSET_MS / 1000));
    const pkt = PacketCreator.getClock(sec);
    for (let i = 0; i < MAPS.length; i++) {
        const id = MAPS[i];
        if (mapFactory().isMapLoaded(id)) {   // ← 关键：仅在已加载时广播
            getMap(id).broadcastMessage(pkt);
        }
    }
}
```

**原因**：用 `isMapLoaded` 守卫避免广播倒计时时意外加载空地图。倒计时提前量解决客户端 00:00 与事件触发之间的时序偏差。

#### ⑤ 区分全局事件与 EIM 事件

| 类型 | 示例 | 地图生命周期 | 释放策略 |
|------|------|-------------|---------|
| 全局事件 | Boats, Trains, Elevator | 永久循环，多玩家共享 | ③ pin 保护航行期间 + ② 守卫避免空载 |
| EIM 事件 | KerningTrain, Hak | 单玩家/单队伍实例，`eim.dispose()` 结束 | 自动管理，无需额外处理 |

EIM 事件（`setup()` 返回 `eim`）的地图由 EventInstanceManager 内部管理，`eim.dispose()` 时自动清理，不受 Channel 缓存驱逐影响。

#### ⑥ 多车厢交替运行事件（电梯）的倒计时陷阱

电梯有两个车厢交替运行。`goingUpNow` 和 `goingDownNow` 各移动一个车厢。**传送门必须把玩家送到"下一班出发"的车厢**，否则玩家看到的倒计时结束后，发车的却是另一个车厢。

```javascript
// ❌ 错误：下层玩家进入 222020110，但 goingUpNow 移动的是 222020210（上层车厢）
function goingUpNow() {
    getMap(222020210).warpEveryone(222020211);  // 移的是上层车厢
}
// Portal: 下层玩家 → 222020110 → 倒计时结束 → 啥也没发生！

// ✅ 正确：下层玩家进入的车厢 = goingUpNow 移动的车厢
function goingUpNow() {
    getMap(222020110).warpEveryone(222020111);  // 移的是下层车厢
}
// Portal: 下层玩家 → 222020110 → 倒计时结束 → 被运输 ✅
```

| 发车方向 | 应从哪个车厢 warp | 到达哪个地图 |
|---------|-------------------|-------------|
| 上行（下层→上层） | 222020110 | → 222020111 (运输中) → 222020200 (上层) |
| 下行（上层→下层） | 222020210 | → 222020211 (运输中) → 222020100 (下层) |

通过遵循以上指南，您将能够创建出更加健壮和高效的事件脚本，为玩家带来流畅和丰富的游戏体验。
