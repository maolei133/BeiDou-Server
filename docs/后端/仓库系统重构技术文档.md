# 仓库系统重构技术文档

## 1. 背景与目标

基于《背包仓库持久化改造方案》及现有架构评估，本项目旨在将仓库系统从旧有的 `inventoryitems` 表中剥离，采用 **“中央账本” + “JSON 序列化”** 的新架构。

**核心目标**：
1.  **数据安全**：消除内存驻留导致的回档风险，确保数据实时落地。
2.  **架构解耦**：脱离臃肿的 `inventoryitems` 表，实现独立存储与扩展。
3.  **可溯源**：接入全服统一的 ELK 日志系统，实现可视化审计。
4.  **统一标准**：为全服物品溯源系统奠定基础。

## 2. 全服物品溯源统一方案 (Global Traceability)

针对目前快递、雇佣商店、仓库、背包均未预留溯源 ID 的现状，本方案提出 **“唯一 ID (Unique ID) 懒加载生成策略”**，以确保后续系统的统一性。

### 2.1 ID 生成规则
*   **格式**：采用 **Snowflake (雪花算法)** 生成的 `Long` 类型 ID。
*   **唯一性**：全服唯一，一旦生成，伴随物品整个生命周期，不可变更。

### 2.2 实施策略：懒加载与补全 (Lazy Generation & Backfill)
由于历史数据没有 ID，我们采取“**接触即生成**”的策略：

1.  **内存模型升级**：
    *   立即修改服务端核心 `Item` 类，增加 `uniqueId` 字段。
    *   加载旧数据时，该字段为 `null`。

2.  **流转时生成 (关键点)**：
    *   当物品从 **背包 (旧系统)** 进入 **仓库/雇佣商店 (新系统)** 时：
        *   检查 `Item.uniqueId`。
        *   若为 `null`，立即生成一个新的 ID 赋值给它。
        *   将带有新 ID 的物品序列化保存到新系统的数据库中。
    *   当物品从 **仓库/雇佣商店** 返回 **背包** 时：
        *   **必须**保留该 ID。
        *   **前置要求**：需同步给 `inventoryitems` 表新增 `unique_id` 字段，否则返回背包后 ID 会丢失，导致溯源断裂。

## 3. 数据库设计

### 3.1 `storage_items` (仓库物品表)
完全脱离 `inventoryitems`，采用独立表结构。

| 字段名 | 类型 | 说明 |
| :--- | :--- | :--- |
| `id` | BIGINT (PK) | 自增主键 |
| `storage_id` | INT | 关联 `storages.storageid` |
| `unique_id` | BIGINT | **物品唯一溯源ID** (索引)。**独立字段，不在JSON中存储**。 |
| `item_id` | INT | 物品模板ID。**独立字段，不在JSON中存储**。 |
| `quantity` | SMALLINT | 数量 |
| `position` | SMALLINT | 排序槽位 |
| `item_data` | TEXT | JSON 格式存储物品 **除唯一ID和模板ID外的** 完整属性 (如潜能、有效期、制作者等)。 |
| `create_time` | TIMESTAMP | 存入时间 |

### 3.2 `storages` (主表 - 保持现状)
继续使用现有的 `storages` 表存储金币和槽位信息，无需结构变更。

## 4. 日志与审计 (ELK Integration)

不再创建独立的 `storage_transactions` 表，而是将所有操作日志通过 **ELK Stack** 进行统一管理。

*   **日志格式**：JSON 结构化日志。
*   **关键字段**：`action` (STORAGE_STORE, STORAGE_TAKE), `uid`, `item_id`, `storage_id`, `character_id`。
*   **优势**：支持海量日志存储、全文检索、可视化图表（如仓库吞吐量、金币流向图）。

## 5. 核心业务流程改造

### 5.1 数据迁移：懒加载机制 (Lazy Migration)
为了避免停服全量迁移的风险，采用玩家触发式迁移。

1.  **触发时机**：玩家打开仓库 NPC。
2.  **检测**：查询 `storage_items` 表是否有该仓库的数据。
3.  **判断**：
    *   **有数据**：直接加载新表数据（新架构路径）。
    *   **无数据**：
        1.  查询 `inventoryitems` 表中 `type=2` (STORAGE) 且 `accountid=storageid` 的旧数据。
        2.  **若旧数据为空**：视为新仓库，直接初始化。
        3.  **若有旧数据**：
            *   遍历旧物品，转换为新 `Item` 对象。
            *   **生成 ID**：为每个物品生成 `unique_id`。
            *   **写入**：批量插入 `storage_items`。
            *   **清理**：删除 `inventoryitems` 中的旧记录（或标记为已迁移 `migrated=1`，视保守程度而定）。
            *   **日志**：输出一条 `STORAGE_MIGRATION` 日志到 ELK。

### 5.2 存入物品 (Store)
1.  **锁定**：获取仓库锁。
2.  **生成 ID**：检查背包中物品的 `uniqueId`，若无则生成。
3.  **事务开始**：
    *   **背包侧**：从 `inventoryitems` 删除（或减少数量）。
    *   **仓库侧**：
        *   调用 `item.toInfoRtnDTO()` 生成符合规范的JSON。
        *   `INSERT INTO storage_items (storage_id, unique_id, item_id, item_data, ...)`。
4.  **事务提交**。
5.  **日志记录**：调用 `TraceabilityService.log` 输出 `STORAGE_STORE` 日志。
6.  **内存更新**：更新客户端 UI。

### 5.3 取出物品 (Take)
1.  **锁定**：获取仓库锁。
2.  **事务开始**：
    *   **仓库侧**：`DELETE FROM storage_items WHERE id = ?`。
    *   **背包侧**：
        *   从数据库记录中获取 `item_id` 和 `item_data`。
        *   调用 `ItemConverter.restoreItemFromDTO` 将JSON反序列化为 `Item` 对象。
        *   **保留 ID**：确保 `Item` 对象携带 `unique_id`。
        *   插入 `inventoryitems`。
3.  **事务提交**。
4.  **日志记录**：调用 `TraceabilityService.log` 输出 `STORAGE_TAKE` 日志。

## 6. 开发计划与注意事项

### 6.1 关键路径
1.  **基础类库升级**：
    *   修改 `Item` 类，增加 `uniqueId` 字段。
    *   实现 `SnowflakeIdGenerator` 工具类。
2.  **数据库变更**：
    *   创建新表 `storage_items`。
    *   同步修改 `inventoryitems` 表，增加 `unique_id` 字段。
3.  **日志接入**：集成 Log4j2 JSON Layout，对接 ELK。
4.  **Service 层重构**：实现迁移逻辑和事务控制。

### 6.2 管理后台支持 (gms-ui)
*   **查询接口**：通过调用 Elasticsearch API 全局搜索物品位置。
*   **日志审计**：嵌入 Kibana Dashboard 展示物品流转时间轴。
