## 2. 统一响应目标落点

目标响应结构：

```json
{
  "code": 20000,
  "message": "操作成功",
  "data": {},
  "timestamp": 1678886400000,
  "path": "/api/user/login"
}
```

当前最接近统一响应落点的是：

- `gms-server/src/main/java/org/gms/model/dto/ResultBody.java`
  - 当前字段：`code`、`message`、`responseId`、`data`
  - 当前成功码：从 `BizExceptionEnum.SUCCESS` 取值，已经是 `20000`
  - 缺口：没有 `timestamp`、`path`；存在额外字段 `responseId`；`error(String)` 默认使用 `-1`；错误构造过程会尝试读取请求体生成 `responseId`，失败时使用 `log.error`。
- `gms-server/src/main/java/org/gms/exception/BizExceptionEnum.java`
  - 当前 `SUCCESS(20000, ...)` 已满足成功码要求。
  - 当前失败码与规范不一致，详见第 3 节。
- `gms-server/src/main/java/org/gms/exception/GlobalExceptionHandler.java`
  - 当前已作为异常响应入口返回 `ResultBody`。
  - 缺口：所有异常详情统一 `logger.error`；未拆分业务失败、认证失败、权限不足、参数校验、资源不存在与系统错误；`RuntimeException` 返回 `40000` 且直接暴露 `e.getMessage()`。

建议统一响应的最小落点：优先在 `ResultBody` 增加 `timestamp`、`path` 并保留 `responseId` 作为兼容字段；所有成功/错误工厂方法仍通过 `ResultBody` 输出，避免大范围 Controller 签名变更。

## 3. 当前响应结构与业务码不一致清单

| 位置 | 当前情况 | 与目标不一致 | 建议归类 |
| --- | --- | --- | --- |
| `ResultBody` | 字段为 `code/message/responseId/data` | 缺少 `timestamp/path`，多 `responseId` | 基础响应结构 |
| `ResultBody.error(String)` | 默认 code 为 `-1` | 未纳入规范业务码 | 业务失败默认码 |
| `BizExceptionEnum.BODY_NOT_MATCH` | `40000` | 规范参数校验为 `10001` | 参数/请求体错误 |
| `BizExceptionEnum.REQUEST_METHOD_SUPPORT` | `40001` | 规范未列该码，建议按参数/方法错误归入 `10001` 或新增文档说明 | 请求方法错误 |
| `BizExceptionEnum.ILLEGAL_PARAMETERS` | `40002` | 规范参数校验为 `10001` | 参数校验失败 |
| `BizExceptionEnum.NOT_FOUND` | `40004` | 规范资源不存在为 `40404` | 资源不存在 |
| 认证失败 | `AuthEntryPointJwt` 使用 HTTP 401 `sendError` | 未返回统一 JSON；无 `code/message/data/timestamp/path` | 认证失败 `20002` |
| 权限不足 | Spring Security 仅配置 `authenticationEntryPoint`，未配置 `accessDeniedHandler` | 403 路径未统一到 `30001` JSON | 权限不足 `30001` |
| `GlobalExceptionHandler` 业务异常 | `BizException` 被记录为 `ERROR` | 业务失败应为 `WARN/INFO` | 日志级别 |
| `GlobalExceptionHandler` 静态资源/资源不存在 | 未专门处理 `NoResourceFoundException` | 资源不存在应为 `40404`，日志 `INFO` | 资源不存在 |
| `GlobalExceptionHandler` 参数校验 | 未专门处理 `MethodArgumentNotValidException` / `ConstraintViolationException` | 参数错误应为 `10001`，日志 `WARN` | 参数校验 |
| `RuntimeException` 处理 | 返回 `BODY_NOT_MATCH(40000)` 且 message 为异常原文 | 系统异常应为 `50000`；业务异常不应走运行时兜底；不宜暴露系统异常原文 | 系统错误兜底 |
| `HiredMerchantController` | 直接返回 `List` / `String` | 完全绕过 `ResultBody` | Controller 返回结构 |
| `ConfigController.exportYml` | 返回 `ResponseEntity<Resource>` 文件下载 | 非 JSON；可能是合理例外但需文档化 | 文件下载例外 |
| `StorageController.transferItem` | 返回 `ResultBody.error("该功能暂未实现")` | 默认 code `-1` | 未实现业务失败 |
| `TraceabilityController.updateTraceabilityConfig` | 返回 `ResultBody.error("未能找到...")` | 默认 code `-1` | 业务失败 |
| `LogSystemController` | 多处 `throw new RuntimeException(...)` | 可预期配置/参数/文件错误会被按运行时异常记录 `ERROR` 且返回 `40000` | 日志/配置接口业务失败 |

## 4. 当前主要类基线

### 4.1 `ResultBody`

路径：`gms-server/src/main/java/org/gms/model/dto/ResultBody.java`

现状：

- 成功工厂：`success()`、`success(T data)`、`success(SubmitBody<?> request, T data)`。
- 成功码已通过 `BizExceptionEnum.SUCCESS` 固定为 `20000`。
- 错误工厂：支持 `BaseErrorInfoInterface`、`message`、`code/message`、`HttpServletRequest` 重载。
- 会为响应填充 `responseId`；对 POST JSON 请求会读取 body 中 `requestId`。

缺口：

- 没有 `timestamp` 和 `path`。
- `error(String)` 默认 `-1`，会产生非规范业务码。
- 读取请求体失败时使用 `log.error`，此类失败更适合作为 `WARN` 或 `DEBUG`，避免业务失败构造响应时污染 `ERROR`。

### 4.2 `BizException` / `BizExceptionEnum`

路径：

- `gms-server/src/main/java/org/gms/exception/BizException.java`
- `gms-server/src/main/java/org/gms/exception/BizExceptionEnum.java`

现状：

- `BizException` 是当前业务异常类，项目没有单独的 `BusinessException` 类；后续文档中的 `BusinessException` 可映射为当前 `BizException` 或通过兼容别名迁移。
- `BizException.fillInStackTrace()` 返回自身，业务异常不填充堆栈，适合业务失败场景。
- `RequireUtil` 大量抛出 `BizExceptionEnum.ILLEGAL_PARAMETERS(40002)`。

缺口：

- 业务码与规范不一致：参数类仍是 `40002`，资源不存在是 `40004`。
- `new BizException(String)` 不设置 `errorCode`，经 `GlobalExceptionHandler` 可能返回 null code。
- 部分服务把资源不存在、参数错误、状态冲突都归入 `ILLEGAL_PARAMETERS`，需要后续按模块细分，但不应在本次基线任务大范围改业务逻辑。

### 4.3 `GlobalExceptionHandler`

路径：`gms-server/src/main/java/org/gms/exception/GlobalExceptionHandler.java`

现状：

- 捕获 `BizException`、`RuntimeException`、`ServletException`、`Exception`。
- 所有异常都调用 `logExceptionDetails`，该方法统一 `logger.error(..., e)`。
- `RuntimeException` 兜底返回 `BODY_NOT_MATCH(40000)` 和异常原文。

缺口：

- 业务异常被记录为 `ERROR`，与业务失败 `WARN/INFO` 规范冲突。
- 没有专门处理参数校验、认证失败、权限不足、资源不存在。
- 通用运行时异常不应返回 `40000`，应统一为 `50000` 并隐藏内部异常原文。
- 当前日志包含 IP、用户、路径、User-Agent，未发现 token 输出，但后续要注意不要记录 Authorization header、密码、完整请求体。

### 4.4 认证与权限异常

路径：

- `gms-server/src/main/java/org/gms/aop/AuthEntryPointJwt.java`
- `gms-server/src/main/java/org/gms/util/JwtUtils.java`
- `gms-server/src/main/java/org/gms/aop/AuthTokenFilter.java`
- `gms-server/src/main/java/org/gms/config/SpringSecurityConfig.java`

现状：

- `AuthEntryPointJwt`：认证失败记录 `logger.error`，然后 `response.sendError(401, "错误：未经授权的访问")`。
- `JwtUtils.validateJwtToken`：签名无效、格式错误、过期、不支持、空参数全部 `logger.error`，返回 `false`。
- `AuthTokenFilter`：捕获所有异常后 `logger.error("Filter error", e)` 并关闭输入/输出流，未输出统一 JSON。
- `SpringSecurityConfig`：只配置 `authenticationEntryPoint(unauthorizedHandler)`，没有显式 `accessDeniedHandler`。

缺口：

- Token 过期/无效属于可预期认证失败，应返回统一 JSON，业务码 `20002`，日志 `WARN` 或 `INFO`。
- 权限不足应返回 `30001`，日志 `WARN`。
- 认证失败不应使用 `sendError` 生成容器默认错误结构。
- 过滤器不应吞掉异常并直接关闭流；应让 Spring Security 入口或统一响应处理可控输出。

## 6. 需优先改造的后端类和接口

按最小改造边界与风险排序：

1. `ResultBody`
   - 增加 `timestamp`、`path`。
   - 将 `error(String)` 默认 code 从 `-1` 调整为规范业务码，建议 `10001` 或新增明确的通用业务失败码并同步文档。
   - 保留 `responseId` 作为兼容字段，避免一次性破坏前端或请求链路。

2. `BizExceptionEnum` / `BizException`
   - 将参数错误、资源不存在等常用码对齐规范：`10001`、`40404`、`50000`。
   - 为认证失败 `20002`、权限不足 `30001` 增加枚举。
   - 修复 `BizException(String)` 缺省 code，避免 null code。

3. `GlobalExceptionHandler`
   - `BizException`：返回统一结构，日志 `WARN` 或按码分 `INFO/WARN`。
   - 参数校验：新增 `MethodArgumentNotValidException`、`ConstraintViolationException`、`MissingServletRequestParameterException` 等处理，返回 `10001`。
   - 资源不存在：新增 `NoResourceFoundException`，返回 `40404`，日志 `INFO`。
   - 权限不足：新增 `AccessDeniedException`，返回 `30001`，日志 `WARN`。
   - 系统异常：`Exception` / 非业务 `RuntimeException` 返回 `50000`，日志 `ERROR` 且保留完整堆栈。

4. 认证安全入口
   - `AuthEntryPointJwt`：不要 `sendError`；直接写统一 JSON，code `20002`，日志 `WARN/INFO`。
   - `JwtUtils`：Token 过期、无效、空参数不再 `ERROR`；调整为 `WARN/INFO` 或让上游统一处理。
   - `AuthTokenFilter`：避免把认证可预期失败刷成 `ERROR` 并关闭响应流。
   - `SpringSecurityConfig`：补充 `accessDeniedHandler`，统一权限不足 `30001`。

5. Controller 最小接口改造
   - `HiredMerchantController`：统一 `ResultBody` 返回，移除方法内字符串错误协议。
   - `StorageController.transferItem`：避免 `ResultBody.error(String)` 产生 `-1`。
   - `TraceabilityController.updateTraceabilityConfig`：避免 `ResultBody.error(String)` 产生 `-1`。
   - `LogSystemController`：把可预期配置/参数/文件错误从 `RuntimeException` 迁移到 `BizException` 或专门异常码，避免全量 `ERROR`。

## 7. 最小改造边界建议

本轮后续实现建议分两步推进，避免高风险一次性重构：

### 第一步：基础协议和异常入口

- 只改 `ResultBody`、`BizExceptionEnum`、`BizException`、`GlobalExceptionHandler`、认证安全入口。
- 不改业务服务逻辑，不调整数据库、脚本、WZ、游戏服核心流程。
- 保留 Controller 现有方法签名，依靠统一异常入口和响应工厂补齐 `timestamp/path`。
- 对 `responseId` 先兼容保留，待前端确认后再决定是否移除。

### 第二步：少量高优先级接口修边

- 改 `HiredMerchantController` 的返回结构。
- 改 `StorageController`、`TraceabilityController` 的 `ResultBody.error(String)`。
- 梳理 `LogSystemController` 中明显属于业务失败的 `RuntimeException`。
- 文件下载接口如 `ConfigController.exportYml` 保留 `ResponseEntity<Resource>`，只统一错误路径。

## 9. 剩余风险与需决策项

- 是否允许保留 `responseId`：建议短期保留，避免破坏已有 `SubmitBody.requestId` 调用链；长期可由前端确认后迁移。
- `ResultBody.error(String)` 默认码应定为 `10001` 还是新增通用业务失败码：需把关人确认。当前规范未提供通用业务失败码。
- 旧业务码 `40000/40001/40002/40004` 是否直接改值：直接改会影响前端或第三方调用兼容性；建议先对齐文档和前端拦截器，再执行。
- 文件下载、静态资源等非 JSON 响应是否全部纳入例外清单：建议明确文档化。
- `LogSystemController` 部分运行失败到底属于业务失败还是系统异常，需要按具体操作确认；例如 Docker 控制能力缺失偏业务/环境配置失败，Loki 查询网络异常可能按系统/依赖异常处理。
