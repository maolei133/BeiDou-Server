# 物品流转溯源系统设计文档

## 1. 系统目标

物品流转溯源系统旨在记录服务器内**有价值物品**的全生命周期行为，包括其产生、转移、消耗和消失的每一个环节。通过本系统，可以实现以下目标：

- **问题排查**: 当出现物品丢失、异常复制等问题时，能够快速追溯物品的完整流转路径，定位问题根源。
- **数据分析**: 分析服务器内稀有物品的产出与消耗情况，为游戏经济平衡提供数据支持。
- **玩家支持**: 为客服人员提供工具，在处理玩家相关的物品纠纷时，能够提供准确、可靠的证据。

## 2. 核心设计 (V1)

> **注意**: 以下为系统的初始设计。关于最新的动态配置化架构，请参阅本文档的 **`## 4. V2版本：动态配置化改造`** 章节。

### 2.1 双重记录机制

为结合数据库的持久化存储优势与Loki日志系统强大的实时查询能力，物品溯源系统采用**双重记录**机制。

1.  **主要数据源 (数据库)**: `item_trace_logs` 数据库表是物品流转的权威、永久记录。
2.  **辅助查询渠道 (Loki)**: 所有写入数据库的溯源信息，会**同时**向Loki日志系统写入一条结构化日志，作为并行的查询和监控渠道。

`TraceabilityService.log()` 方法将统一负责数据库的写入和Loki日志的发送。

### 2.2 数据库表结构 (`item_trace_logs`)

核心数据存储在 `item_trace_logs` 表中，记录了每一次物品状态变更的完整信息。

- **`id`**: 记录ID，自增主键。
- **`uid`**: 物品的全局唯一ID。在数据库中存储为 `BIGINT` 类型，但在返回给前端时，会序列化为 `String` 类型，以避免 JavaScript 精度丢失。
- **`item_id`**: 物品的模板ID。
- **`action_type`**: **(V3.2更新)** 行为的领域或模块（枚举），如 `INVENTORY`, `STORAGE`, `NPC_SHOP` 等。
- **`action_source`**: **(V3.2更新)** 格式化后的行为来源详细描述，由 `ActionSourceType` 枚举和参数动态生成。
- **`character_id`**: 操作角色的ID。
- **`account_id`**: 操作角色的账号ID。
- **`quantity_change`**: 数量变化。正数表示增加，负数表示减少。
- **`item_snapshot`**: 物品在本次行为发生**后**的状态快照 (JSON)。
- **`timestamp`**: 行为发生的时间戳。

### 2.3 (V3.2) 行为类型与来源规范

为了提供精确、结构化的溯源信息，系统引入了 `ActionType` 和 `ActionSourceType` 两个枚举。

- **`ActionType` (行为类型)**: 定义了物品操作的宏观领域或模块。
- **`ActionSourceType` (行为来源)**: 定义了行为发生的具体场景，并包含一个格式化字符串，用于生成详细的 `action_source` 描述。

| `ActionType` | `ActionSourceType` | 格式化字符串               | 示例                         |
| :--- | :--- |:---------------------|:---------------------------|
| `INVENTORY` | `PLAYER_DROP` | `丢弃物品`               | `丢弃物品`                     |
| | `PLAYER_PICKUP` | `拾取物品`               | `拾取物品`                     |
| `STORAGE` | `STORAGE_PUT_IN` | `存入仓库`               | `存入仓库`                     |
| | `STORAGE_TAKE_OUT` | `从仓库取出`              | `从仓库取出`                    |
| `NPC_SHOP` | `NPC_SHOP_BUY` | `从 [%d] %s 购买`       | `从 [1012100] 武器商人 购买`      |
| | `NPC_SHOP_SELL` | `出售给 [%d] %s`               | `出售给 [1012100] 武器商人`       |
| `PLAYER_SHOP` | `MERCHANT_BUY` | `从 [%d] %s 商店购买`      | `从 [10001] 小明的商店 商店购买`     |
| | `MERCHANT_RETURN`| `从 [%d] %s 商店取回`      | `从 [9900001] 弗雷德里克 商店取回`   |
| `ITEM_USAGE` | `ITEM_USE` | `使用: [%d] %s × %d` | `使用: [2000005] 超级药水 × 1` |

| | `SYSTEM_QUEST_REWARD` | `任务奖励: [%d] %s`       | `任务奖励: [1001] 新手任务`        |
| `ADMIN` | `ADMIN_CREATE` | `GM %s 通过命令(%s)创建`   | `GM Admin 通过命令(item)创建`    |

### 2.4 Loki 日志规范 (用于辅助查询)

发送到Loki的日志遵循 `AuditLogger` 的标准。由于 `AuditLogger` 会自动注入当前操作的**角色、账号、IP、地图**等上下文信息，因此只需要在日志中记录**数据库未显式分离的业务核心信息**。

- **日志模块**: `LogModule.ITEM`
- **核心业务字段 (`MapMessage`)**:

| 字段名 (Key)   | 说明 | 数据类型 | 备注 |
|:------------| :--- | :--- | :--- |
| `msg`       | 行为的文字描述 | String | **(推荐)** 直接复用为数据库准备的 `action_source` 字段内容。 |
| `itm`       | 物品的模板ID | Integer | Loki 标准字段。 |
| `itmName`   | 物品名称 | String | 便于在Loki中直接搜索。 |
| `cnt`       | 数量变化 | Integer | Loki 标准字段。正数增加，负数表示减少。 |
| `itmData`   | 物品属性快照 | String (JSON) | 记录物品的详细属性，用于问题排查。 |
| `targetChr` | 交易对方角色名 | String | (可选) 交易、赠送等场景使用。 |

### 2.5 价值品过滤机制 (V1 - 已废弃)

> **注意**: 此处为旧的硬编码过滤机制，已被V2版本的动态配置所取代。

本系统**不会记录所有物品的流转**，只有被判定为“有价值的物品”才会被记录。判断标准与物品找回系统完全一致。

- **统一判断入口**: `InventoryManipulator.isValuableForRecovery(Item item)`
- **判断细则**:
    1.  **现金道具**: 总是记录。
    2.  **装备 (Equip)**: 满足以下**任一**条件：
        - 穿戴等级 >= 120。
        - 已砸卷次数 > 1 或 成长等级 > 1。
        - 当前属性高于白板属性。
    3.  **消耗品 (USE)**: 记录卷轴、技能书、母书、高价值投掷武器、召唤包等。
    4.  **其他/设置 (ETC / SETUP)**: 记录椅子、特殊任务道具等。

### 2.6 (V3.2) 统一的记录入口

所有需要记录物品流转的地方，都必须调用 `TraceabilityService` 提供的 `log()` 方法。

- **推荐使用**:
  ```java
  log(Item item, Character character, ActionType domainType, ActionSourceType specificActionType, int quantityChange, Object... sourceArgs)
  ```
  此方法会自动根据 `ActionSourceType` 的格式化字符串生成 `action_source`。

- **通过ID记录 (当 `Character` 对象不可用时)**:
  ```java
  log(Item item, int accountId, int characterId, int mapId, ActionType domainType, ActionSourceType specificActionType, int quantityChange, String memo, Object... sourceArgs)
  ```

- **已废弃**:
  ```java
  @Deprecated
  log(Item item, Character character, ActionType actionType, String actionSource, ...)
  ```
  旧的、直接接收 `actionSource` 字符串的 `log` 方法已被废弃，以强制使用结构化的 `ActionSourceType`。

### 2.7 前端LogQL查询规范 (V3.3)

为确保前端（特别是日志仪表盘 `/log/dashboard`）能够正确、高效地查询Loki日志，特此规范LogQL的构建逻辑。

-   **严格区分标签与字段**:
    -   **标签 (Label)**: 用于高性能的流选择。`job`, `mod`, `act`, `actsou` 是预设的索引标签。所有对这些键的过滤，**必须**放在流选择器 `{...}` 之内。
        -   *正确示例*: `{job="gms-audit", mod="SHOP"}`
        -   *错误示例*: `{job="gms-audit"} | mod="SHOP"`
    -   **字段 (Field)**: 日志正文（JSON内容）中的键值对。对这些字段的过滤，**必须**在 `| json` 解析器之后进行。
        -   *正确示例*: `... | json | mapName="射手村"`
        -   *错误示例*: `{..., mapName="射手村"}`

-   **动态过滤器的构建逻辑**:
    -   前端可视化构建器支持**多个动态过滤条件**。
    -   在生成查询时，前端会遍历所有条件，根据字段名是否属于预定义的`LOKI_LABELS`列表，来决定该条件是作为**标签选择器**还是**管道过滤器**。

-   **测试查询的实现**:
    -   仪表盘的“测试语句”功能，会根据当前设置的过滤条件，**独立构建一个用于获取原始日志的流查询**（即 `{...} | ... | json` 格式），并附带时间范围 (`range`) 参数。
    -   这确保了测试的是数据源的过滤能力，而不是最终的聚合查询。

-   **状态持久化**:
    -   为了实现图表编辑的精确恢复，前端现在会将结构化的**构建器状态对象 (`queryBuilder`)** 与图表配置一同保存。
    -   加载图表进行编辑时，会优先从这个状态对象恢复UI，而不是从最终的LogQL查询字符串中反向解析。

## 3. 开发者规范与集成点 (V3.2)

### 3.1 开发者规范
1.  **统一调用**: 当开发新功能涉及有价值物品的流转时，必须在相应的代码位置调用 `TraceabilityService.log()` 方法。
2.  **遵循格式**: 调用 `log()` 方法时，必须传入正确的 `ActionType` 和 `ActionSourceType` 枚举，并提供 `sourceArgs` 所需的参数。
3.  **禁止绕过**: 严禁在项目中直接操作 `item_trace_logs` 表或单独调用 `AuditLogger` 记录溯源日志。所有操作必须通过 `TraceabilityService`。

## 4. V2版本：动态配置化改造

### 4.1 核心架构

为实现最大的灵活性，整个溯源系统的行为由一个存储在`game_config`表中的动态JSON配置 (`config_code = 'traceability_rules'`) 驱动。

- **`org.gms.service.TraceabilityConfigService` (新增)**: 溯源配置的**唯一权威来源**。
    - 内部硬编码一个**默认JSON配置**。
    - 负责从`GameConfig`获取配置，若配置不存在，则返回并使用默认配置。
- **`org.gms.model.pojo.TraceabilityRules` (新增)**: JSON映射的强类型POJO实体类。
    > **新增字段处理指引**: 如果需要新增溯源判断条件或配置开关：
    > 1. 更新 `TraceabilityRules` 类，在对应的内部类中增加字段并添加中文注释。
    > 2. 更新 `TraceabilityConfigService` 中的 `DEFAULT_TRACEABILITY_RULES` 字符串，配置相应的默认值和注释。
    > 3. 前往 `InventoryManipulator.isValuableForRecovery()` 等业务判断点，读取新字段并编写实际验证逻辑。
    > 4. 若涉及前端管理界面，则更新前端 `dashboard/config` 的表单。
- **`org.gms.controller.TraceabilityController` (新增)**: 对外提供API，用于获取和更新溯源配置，以及查询统计数据。
- **`org.gms.service.TraceabilityService`**: 依据`TraceabilityConfigService`提供的规则，执行具体的溯源记录逻辑。
- **`org.gms.net.server.task.TraceabilityCleanupTask` (新增)**: 后台定时任务，根据配置规则清理过期的数据库日志。

### 4.2 动态配置规则 (JSON结构)

存储在`game_config`表中的`traceability_rules`配置项，其`config_value`为一个JSON对象，结构如下：

```json
            {
  "ENABLED": {
    "DATABASE": true, // 是否启用写入到数据库表ITEM_TRACE_LOGS
    "LOKI": true      // 是否启用并行写入Loki日志系统
  },
  "RECORDINGTARGETS": {
    "VALUABLE": { "DATABASE": true, "LOKI": true },     // 有价值物品(通过下方的VALUECONDITIONS判断)的记录目标
    "NONVALUABLE": { "DATABASE": false, "LOKI": false } // 无价值物品(普通物品)的记录目标
  },
  "RETENTION": {
    "VALUABLE": { "DAYS": 90, "MAXCOUNT": 1000000 },    // 有价值物品在数据库中保留的最大天数和最大条数
    "NONVALUABLE": { "DAYS": 7, "MAXCOUNT": 500000 }    // 无价值物品在数据库中保留的最大天数和最大条数
  },
  "TEMPORARYDISABLES": {
    "LOOT": { "ENABLED": true, "DISABLEUNTIL": null },     // 是否临时禁用 怪物掉落/拾取 记录，以及禁用截止时间
    "SHOP_BUY": { "ENABLED": true, "DISABLEUNTIL": null }  // 是否临时禁用 商店购买 记录，以及禁用截止时间
  },
  "LOGACTIONSWITCHES": {
    "TRADE": true,       // 是否记录 玩家间交易 (TRADE)
    "DROP": true,        // 是否记录 玩家丢弃 (DROP)
    "SELL": true,        // 是否记录 玩家出售给NPC (SELL)
    "STORAGE_IN": true,  // 是否记录 存入仓库 (STORAGE_IN)
    "STORAGE_OUT": true, // 是否记录 从仓库取出 (STORAGE_OUT)
    "GM_CREATE": true    // 是否记录 GM通过命令创造物品 (GM_CREATE)
  },
  "VALUECONDITIONS": {
    "EQUIP": {
      "MINLEVEL": 120,               // 装备最低穿戴等级限制（满足即视为有价值）
      "MINUPGRADESLOTSUSED": 1,      // 装备最低已砸卷次数（满足即视为有价值）
      "MINGROWTHLEVEL": 1,           // 装备最低成长等级（满足即视为有价值）
      "MINVICIOUSHAMMERUSED": 1,     // 装备最低金锤子使用次数（满足即视为有价值）
      "MINSTATSABOVEBASE": 1         // 装备属性总和(不含HP/MP)超过白板属性的最低值（满足即视为有价值）
    },
    "ITEM": {
      "THROWINGWEAPONS": {     // 投掷武器
        "ENABLED": true,       // 是否启用
        "MINATTACKPOWER": 20,  // 投掷武器最小攻击威力
        "MINATTACKPOWER_BULLET": 15 // 投掷武器最小攻击威力(弹药)
      },
      "POTIONS": {
        "ENABLED": true,       // 是否启用
        "MINTOTALSTATBONUS": 50 // 强化药水最小总属性增益 >= 50，视为有价值
      },
      "ITEMTYPES": [
        { "T": 204, "D": "所有强化卷轴" , "ENABLED": true },
        { "T": 228, "D": "所有技能书" , "ENABLED": true },
        { "T": 229, "D": "所有能手册" , "ENABLED": true },
        { "T": 210, "D": "所有召唤包" , "ENABLED": true },
        { "T": 301, "D": "所有椅子" , "ENABLED": true }
      ],
      "SPECIFICITEMIDS": [] // 强制视为有价值的特定物品ID列表 (如混沌卷轴)
    }
  },
  "PERFORMANCE": {
    "IGNOREDMAPIDS": [] // 忽略记录所有事件的地图ID列表 (如自由市场)
  }
}
```

#### JSON结构详解

- `ENABLED`: **总开关**，分别控制数据库和Loki的记录功能。
- `RECORDINGTARGETS`: **记录目标**。可精细化控制“有价值”和“无价值”物品的日志分别写入哪里（数据库/Loki/两者都写/都不写）。
- `RETENTION`: **保留策略**。
    - `DAYS`: 日志在数据库中的最大保留天数。
    - `MAXCOUNT`: 该类别日志在数据库中的最大存储条数。清理任务会优先删除超期的，然后删除超量的。
- `TEMPORARYDISABLES`: **临时禁用开关**。用于临时屏蔽某些高频行为的记录。
    - `DISABLEUNTIL`: 如果设置为未来的时间戳 (ISO 8601格式)，则在该时间点之前，该行为的记录将被临时屏蔽。
- `LOGACTIONSWITCHES`: **行为开关**。决定一个`ActionType`是否需要被处理。
- `VALUECONDITIONS`: **价值判断条件**。定义了“有价值物品”的标准。
    > **[警告]** 此配置与“物品找回系统”共享。修改此处的规则将直接影响到哪些物品在被出售或丢弃后，有资格进入物品找回列表。
    - `EQUIP` 装备价值判断：
        - `MINLEVEL`: 装备穿戴等级大于等于此值。
        - `MINUPGRADESLOTSUSED`: 装备已砸卷次数大于等于此值。
        - `MINGROWTHLEVEL`: 装备成长等级大于等于此值。
        - `MINVICIOUSHAMMERUSED`: 装备金锤子使用次数大于等于此值。
        - `MINSTATSABOVEBASE`: 装备当前属性总和(不含HP/MP)超过白板属性大于等于此值。
    - `ITEM` 消耗/其它物品价值判断：
        - `SCROLLS`, `SKILLBOOKS`, `MASTERYBOOKS`: 分别控制是否记录所有卷轴、技能书、能手册。
        - `THROWINGWEAPONS`: 投掷武器（飞镖/子弹）的价值判断。
            - `ENABLED`: 是否启用此判断。
            - `MINATTACKPOWER`: 攻击力大于等于此值则视为有价值。
        - `POTIONS`: 增益药水的价值判断。
            - `ENABLED`: 是否启用此判断。
            - `MINTOTALSTATBONUS`: 药水提供的属性（力/敏/智/运/物攻/魔攻）总和大于等于此值则视为有价值。
        - `ITEMTYPES`: 检测物品ID前缀的列表配置。例如 `T=207` 表示所有ID以 `207` 开头的物品（投掷武器）。
        - `SPECIFICITEMIDS`: 强制视为有价值的物品ID列表（例如混沌卷轴 `2049100`）。
- `PERFORMANCE`: **性能调优**。
    - `IGNOREDMAPIDS`: 在这些地图中发生的所有事件都将被忽略（例如自由市场 `910000000`）。

### 4.3 日志清理机制

- **数据库**: `TraceabilityCleanupTask`定时任务会严格按照`RETENTION`配置中的`DAYS`和`MAXCOUNT`清理`item_trace_logs`表。注意：数据库日志清理现在统一根据设置的时间或数量进行物理删除。
- **Loki**: **应用层无法也禁止删除Loki日志**。Loki的日志保留期由其自身的全局配置决定，需由运维人员独立设置。

### 4.5 后端数据模型

-   **`ItemTraceLogsDO`**: 物品流转日志的数据库实体类。
    -   `uid` 字段类型为 `BIGINT`，对应数据库中的 `bigint` 类型。
    -   为了避免前端 JavaScript 精度丢失，使用 `@JsonSerialize(using = ToStringSerializer.class)` 注解，在序列化为 JSON 时将 `uid` 转换为字符串。
-   **`ItemRecoveryLogsDO`**: 物品找回日志的数据库实体类。
    -   `uid` 字段类型为 `BIGINT`，对应数据库中的 `bigint` 类型。
    -   为了避免前端 JavaScript 精度丢失，使用 `@JsonSerialize(using = ToStringSerializer.class)` 注解，在序列化为 JSON 时将 `uid` 转换为字符串。

### 4.6 核心逻辑

-   **`TraceabilityService.queryLogs(TraceabilityQueryDTO queryDTO)`**: 根据查询条件分页查询物品溯源日志。
    -   从 `queryDTO` 中获取查询参数，包括 `uid`（String 类型）。
    -   如果 `uid` 不为空，则将其解析为 `Long` 类型，并用于数据库查询。
-   **`TraceabilityService.log(...)`**: 记录物品流转日志。
    -   接收 `Item` 对象，从中获取 `uid`（long 类型），并直接存储到数据库中。

### 4.7 行为类型 (ActionType) 和 行为来源 (ActionSource) 的设计与规划

-   **行为类型 (ActionType)**: 使用枚举类型，定义了所有可能的物品流转行为。
    -   后端提供 `GET /v1/traceability/action-types` 接口，根据请求的语言环境返回本地化后的行为类型列表。
    -   后端提供 `GET /v1/traceability/action-source-types` 接口，根据请求的语言环境返回本地化后的行为来源列表。
    -   前端通过下拉选择器展示行为类型，避免用户输入错误。
-   **行为来源 (ActionSource)**: 详细的文字描述，包含执行者和目标等完整信息。
    -   目前使用文本输入框进行模糊查询。
